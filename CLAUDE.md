## Build & deploy pipeline

**Always build after changes.** Whenever you finish a set of working-tree edits (Java/XML/resources), run the full pipeline below to completion — bump, assemble, sign, verify, copy the signed APK to `~/tmp/` — without waiting for the user to say "Build". Treat a task as unfinished until it has produced a fresh signed APK on disk. If the build fails, stop and surface the error rather than reporting the change as done.

**Deliver automatically after every build — never ask.** Standing instruction from 白い熊 (2026-08-06), replacing the former "always ask via `AskUserQuestion`" rule: follow the global **`/after-build`** skill and its delivery chain, and do not put a question between the build and the delivery. After a successful build, walk the chain yourself — `adb devices` (**unsandboxed**, per `/adb-check`) → `adb connect 192.168.1.73:5555` → `adb connect skhw:15555` → `scp` to `skhw:~/tmp/` — and deliver **exactly once**, to the first target that answers. Those are all the **same machine**, so never deliver by two paths. Never ask "how should I deliver?" and never ask "is the phone connected?" — the chain answers that itself. Any wireless adb session opened for the batch gets `adb disconnect`ed at the end of it (check `ps` for a live `scrcpy` first). Then say plainly what landed and where.

Output APK is named `shiroikuma-oyokanri_$(tools/fork-version.sh)_arm64-v8a.apk`, e.g. `shiroikuma-oyokanri_4.1.0.2026-06-29.gfc1e7007+089_arm64-v8a.apk`. Always copy the signed APK to `~/tmp/` before pushing to the device, so a record stays on disk.

**The versionName pins the upstream commit we are rebased on (+89).** `custom` follows upstream **master**, whose versionName literal (`4.1.0`) has not moved since 2026-06-29 and will not move until upstream releases — so `4.1.0+088` said nothing whatever about how current the fork was. The name is now `<customBaseVersionName>+<base commit date>.<HH-MM>.g<sha8>+<NNN>`, where the sha is `git merge-base HEAD master` — **the upstream commit our patches sit on**, never our own HEAD (that is what `+N` and the release tag already say) and never `master`'s tip (which overstates the base whenever master is fast-forwarded but `custom` not yet rebased). The timestamp is that commit's **committer date and time in UTC** — never build time, or two builds on one upstream base would disagree — and exists only so the names sort: a bare sha is random text and buries the newest APK mid-list, and a bare date ties whenever two syncs land on one day, handing the ordering straight back to that sha (hence `HH-MM`, 白い熊 2026-08-12). **Two halves that must stay in step**: `upstreamBasePin()` in `app/build.gradle` (Gradle, via `providers.exec` — a plain `ProcessBuilder`/`String.execute()` is a configuration-cache failure, which is why `buildTime()` already does it this way) and **`tools/fork-version.sh`** (shell, the single source of truth for the pipeline and for `tools/bump-build.sh`'s printed line). Both **degrade rather than fail**: no `master` ⇒ no pin, git present but the timestamp unreadable ⇒ `+g<sha>` alone. A missing pin must never cost a build.

**LANDMINE — do NOT reset `customBuildNumber` on an upstream sync in this repo.** The `git-versioning` skill says the counter resets to 1 on each sync; that holds where the upstream commit feeds `versionCode`. Here it does not — `versionCode = customBaseVersionCode * 10000 + customBuildNumber`, and `customBaseVersionCode` (450) only moves when upstream cuts a **release**. Resetting the counter after an ordinary master rebase would therefore drive the versionCode **backwards** and Android would refuse the install as a downgrade. Reset it **only** in the same edit that raises `customBaseVersionCode`; every other rebase just keeps counting, and the pin is what records that upstream moved.

**The build counter is zero-padded to three digits — in the filename AND in `versionName` (+63).** The `/after-build` convention pads the filename so `~/tmp` sorts in build order; `app/build.gradle` must pad too, or the two disagree in the place that matters. Before +63 the file read `+062` while the **manifest** read `+62`, which is what Android and every installer actually show — 白い熊 caught it in shiroikuma-universalinstaller's install dialog. `versionName "${customBaseVersionName}${upstreamPin}+${String.format('%03d', customBuildNumber)}"`, and `tools/bump-build.sh` prints the same by delegating to `tools/fork-version.sh` (it used to render its own `printf '%s+%03d\n'`, which is exactly how a second copy of the format drifts). `versionCode` stays plain integer arithmetic, so upgrade ordering is untouched. Note the `publish-version` skill derives its git tag from the version name, so tags carry the padding from +063 on; earlier published tags (`4.1.0+55`) are **never** retagged.

```bash
# from repo root
export JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64
export PATH="$JAVA_HOME/bin:$PATH"
export ANDROID_HOME=$HOME/android-sdk

tools/bump-build.sh                            # increments customBuildNumber
echo "sdk.dir=$ANDROID_HOME" > local.properties

./gradlew clean
# Filter benign output on BOTH streams; preserve the exit code with pipefail.
set -o pipefail
./gradlew :app:assembleRelease \
    2> >(grep -vE 'ノート:|Note:|\[CXX5304\]' >&2) \
  | grep -vE 'ノート:|Note:|\[CXX5304\]'

UNSIGNED_APK=$(find app/build/outputs/apk/release -name '*-unsigned.apk' | head -1)

# HARD GATE: the embedded server JARs must be present AND non-empty, or ADB mode
# is dead on arrival (see "Server JARs" note below). Refuse to sign otherwise.
for j in assets/am.jar assets/main.jar; do
    sz=$(unzip -p "$UNSIGNED_APK" "$j" 2>/dev/null | wc -c)
    [ "$sz" -gt 0 ] || { echo "FATAL: $j is empty/missing in APK — refusing to ship"; exit 1; }
done

zipalign -p -f 4 "$UNSIGNED_APK" /tmp/am-aligned.apk
apksigner sign --ks ~/.android-keystores/appmanager-custom.jks \
    --ks-key-alias appmanager \
    --ks-pass pass:appmanager123 \
    --key-pass pass:appmanager123 \
    --out /tmp/am-signed.apk /tmp/am-aligned.apk
apksigner verify --verbose /tmp/am-signed.apk 2>&1 | grep -v 'not protected by signature'

# Base version + upstream-base pin + zero-padded counter, from the one place that renders it.
# Never re-derive this from gradle.properties by hand — the pin would be dropped and the
# filename would stop matching the manifest.
apk_name="shiroikuma-oyokanri_$(tools/fork-version.sh)_arm64-v8a.apk"
cp /tmp/am-signed.apk ~/tmp/"$apk_name"

# Deliver straight away — first target that answers, exactly once (see the
# delivery rule above). adb ALWAYS runs unsandboxed.
adb push /tmp/am-signed.apk "/sdcard/tmp/$apk_name"    # or: scp ~/tmp/"$apk_name" skhw:~/tmp/
```

Filter notes:
- `ノート:` / `Note:` are mandatory `javac` summary notes for deprecation/unchecked usage; `-Xlint:none` and `-nowarn` do not suppress them.
- `[CXX5304]` is a benign SDK-XML version-skew message from the NDK pipeline. Brackets must be escaped (`\[CXX5304\]`) for `grep -E`.

**Server JARs (`assets/am.jar` + `main.jar`) — the ADB-mode landmine.** Both are
gitignored and regenerated every build by `:server:create<Variant>ServerJars`
(server/build.gradle), which `d8`-compiles them straight into `app/src/main/assets/`.
`main.jar` is the bootstrap the ADB shell runs to launch AppManager's server; an
empty/missing one makes **ADB mode hang on init then fall back to no-root** (build
+79 shipped a **0-byte main.jar** this way and looked like a code regression — it
was a build race). Two structural guards now prevent it, plus the gate above:
1. **Ordering** — `app/build.gradle` makes `merge<Variant>Assets dependsOn
   :server:create<Variant>ServerJars` via a plain `tasks.matching` edge (the old
   `applicationVariants.mergeAssetsProvider` edge was unreliable under the
   configuration cache — that's how +79 slipped through).
2. **Atomic writes** — server/build.gradle `d8`s each JAR into a **per-variant**
   `server/build/serverjars-tmp/<buildType>/` dir (temp name must keep the `.jar`
   suffix — d8 rejects others; per-variant because release+debug jar tasks run in
   parallel and share nothing), then `Files.move`s it into `assets/`, so a racing
   consumer sees a whole JAR or none, never a partial. Diagnose a suspected recurrence
   with `unzip -p <apk> assets/main.jar | wc -c` (compare a known-good vs bad APK).

## Push workflow

When the user says **"Push"**:
1. `git add -A` (include new files).
2. Show `git status` for the user to review.
3. `git commit -m "<concise imperative title>" -m "<multi-line body describing what changed and why>"`.
4. `git push origin custom` — **never force-push**.
5. Report the resulting commit hash and a one-line summary.

## Translation workflow

The user supplies an English label plus its Japanese translation and where they see it. Procedure:
1. Find the matching string-resource name in `app/src/main/res/values/strings.xml` (e.g. "Frozen apps" → `name="filter_frozen_apps"`).
2. Add `<string name="…">…</string>` to `app/src/main/res/values-ja/strings.xml` under the marker `<!-- Fork: user-supplied Japanese translations -->`.
3. The translation applies wherever that resource is referenced, including the toolbar (via `MainToolbarPrefs.titleForKey`).

## Protected profile (`必要`)

Any app that is a member of an apps profile named **`必要`** is hard-blocked from being frozen and uninstalled. Enforcement sits at the two low-level chokepoints, so no UI path (single-app, batch, profile application, future code) can bypass it.

| Chokepoint | Behaviour |
|---|---|
| `FreezeUtils.freeze(pkg, userId, type)` | Throws `RemoteException` for protected packages. The 2-arg `freeze` delegates to this; all freeze methods (disable/suspend/hide) run after the guard. |
| `PackageInstallerCompat.uninstall(pkg, userId, keepData)` | Returns `false` at the very top, before any work or accessibility dialog. |
| `profiles/ProtectedAppsProfile.java` | Helper. `getProtectedPackages()` unions `packages` from every apps-profile named `必要`. 3 s TTL cache. **Fails open** (a stuck block is worse than briefly missing protection). Call `invalidate()` after profile changes. |

Concrete refusal messages fire at four entry points — the main-list freeze icon, app-details freeze, app-details uninstall, and batch freeze/uninstall — using `R.string.protected_profile_block` (single, `%s` = label) and `R.string.protected_profile_block_multiple` (list, `%s` = names joined with `、`).

## Device policy — hard locks delegated by 白い熊 雫 (`devicepolicy/`)

Everything the Snooping page did before +57 is **soft**: an op we write or a permission we revoke can
be put back by Settings, by another tool, sometimes by the app. 白い熊 made the sister app **白い熊 雫**
(`shiroikuma.shizuku`, repo `shiroikuma-shizuku`) **Device Owner**; it delegates policy scopes to us,
and a decision can then be made **hard**.

- **Two channels, and the split is load-bearing.** `DevicePolicyBridge` covers what the platform will
  delegate (`DELEGATION_PERMISSION_GRANT`, `DELEGATION_PACKAGE_ACCESS`, `DELEGATION_BLOCK_UNINSTALL`)
  and calls the **public SDK with a `null` admin** — no hidden API, no binder relay, and it keeps
  working while 雫 is stopped, because `system_server` persists the delegation. `PolicyApiClient`
  covers what **no scope can carry** (`setPermittedAccessibilityServices`, `addUserRestriction`,
  `setAlwaysOnVpnPackage`, `setCameraDisabled`, `setUserControlDisabledPackages`) via
  `ContentResolver.call` on 雫's provider, authority **`shiroikuma.shizuku.policy`**. **Prefer the
  delegated path wherever it reaches** — routing a delegatable call through 雫 trades a persistent
  grant for a live dependency. Method names on the wire (`status`, `set_accessibility_blocked`,
  `set_user_control_disabled`, `set_user_restriction`, `set_always_on_vpn`, `set_camera_disabled`,
  `clear_all_locks`) are shared with 雫 — **never rename one**.
- **Why a provider call and not a broadcast** (unlike the 保存復元 contract): it is **synchronous** and
  answers with a `Bundle`, which is what a switch the user just tapped needs; and
  `Binder.getCallingUid()` identifies us on the far side, so no shared token is needed — the token in
  保存復元 exists precisely because a broadcast has no trustworthy sender.
- **`setDelegatedScopes` can only be called by the owner app**; there is no `dpm` shell command for it
  (checked against `dpm help` on Android 13 and 15). 白い熊 authorises us in 雫 → Settings → **Feature
  Hub** → **Device policy powers** (a `CollapsiblePreferenceCategory`, **collapsed by default** like
  every category on that page — `android:defaultValue` is read as *defaultExpanded*) → the 白い熊 応用管理
  row → *Allow device-policy powers*. One switch does both halves: 雫's own policy allowlist **and**
  `setDelegatedScopes`.
- **LANDMINE — the CALLEE mints the job id, and the caller must adopt it (白い熊, +116).** Every sister app answers `export`/`import` with `OK:<its own job id>` (`AutomationJobs.begin()`) and broadcasts completion carrying **that** id; `AppDataClient` invented a UUID, sent it, and then filtered replies on it — so the reply arrived, failed the correlation, was dropped, and the transfer sat until the two-minute silence watchdog killed it. A 22 MB ArcaneChat export that had already finished on disk was reported as **"Could not backup"**, which reads as a broken door rather than a broken client. `transfer()` now adopts the returned id (still accepting its own, which costs nothing) and holds terminal replies that arrive **before `call()` returns** in an `unclaimed` map, claiming them the moment the id is known — without that the fix works for a slow export and fails for a fast one.
- **LANDMINE — `setPermissionGrantState` accepts dangerous RUNTIME permissions and nothing else
  (measured 2026-08-01).** Having *a* permission is not enough: `GET_USAGE_STATS` is backed by
  `android.permission.PACKAGE_USAGE_STATS`, protection `signature|privileged|development|appop|
  retailDemo`, so a lock offered on *Read app usage* was accepted by our UI and thrown away by the
  platform. `AppDetailsSnoopingItem.policyLockable` is resolved from the protection level up front
  (`PROTECTION_DANGEROUS`) **and** requires the app to actually request the permission — the same
  discipline `SnoopingResolver#canWritePermission` applies to the ordinary write path. App-op-only
  rows can never be locked and show no padlock at all.
- **Read the lock from the platform, never from our own store.** `isPermissionLocked` asks
  `getPermissionGrantState`; a lock set by 雫 directly, or left by an older build, shows the padlock
  just the same. Every write re-reads afterwards and reports whether it landed;
  `setPackagesSuspended`'s return array is the packages it could **not** touch, so a non-empty return
  is a failure, not a success with a note.
- **LANDMINE — refreshing the card is not refreshing the row.** `loadPolicyState` ends in
  `notifyPolicyChanged`, which invalidates **row 0 only** (the policy card); a row's `policyLocked` is
  filled in by `SnoopingResolver`, i.e. only on a full reload. A lock landed, the toast said
  "Applied", and the padlock kept drawing its stale hollow self. Row-level writes go through
  `runRowPolicy`, which calls `refreshPolicyLockState(packageName)` (the cheap half, needing only the
  package name) and rebinds that row.
- **UI.** A policy card is pinned above the capabilities (`item_app_details_snooping_policy.xml`,
  adapter `TYPE_POLICY` at index 0 — added **only when there is at least one capability row**, because
  `AppDetailsFragment` drives the empty view off the item count). It states whether the powers are
  live and, when not, *why* — no Device Owner on this phone versus authorised in 雫 but not for us —
  carries the **suspend** switch (a harder freeze than hiding) and a pill into *More device-policy
  controls…*. Each capability row gets a **padlock column left of the toggle**, hollow where a lock
  could land and filled where one does, yellow in both states; **tap locks, tap again releases, no
  confirmation either way** (白い熊: the explanation belongs in the legend, not in a dialog dismissed
  every time).
- **`DangerDialog` has two shapes, and the distinction is deliberate.** `confirm` — 危険 heading,
  **Cancel in the positive slot**, destructive choice red in the quiet negative slot — is reserved for
  powers that can leave the phone hard to operate or recover (accessibility blocking, user
  restrictions, always-on VPN lockdown). `confirmReversible` — no heading, normal button placement —
  is for what this page releases in one tap. Calling suspension 危険 was simply wrong: it is undone by
  the same switch that applied it.
- **The way back must always exist.** `clear_all_locks` lives in 雫 because it must work when 応用管理
  is gone, and because the Device Owner can undo what its delegate did by walking a package's
  permissions for anything not at the default grant state — no ledger needed on either side. Our
  fallback releases what this page can see (its own locked rows, suspension, uninstall block) and
  reports honestly when the remote half did not answer.
- **The legend is the documentation.** ⋮ → *What the marks mean* explains the card frame, the remember
  box, the padlock, the status pill and what locking actually does. Add to it rather than inventing a
  new explanatory surface.
- **Remember/forget is NOT a device-policy matter** and no longer sits in that menu. It is the row's
  **long-press**, shown as a small rounded box around the switch (`rememberedBox`, built in code so it
  takes `ForkThemeUtils.getTextColor()`). `AppDetailsViewModel.rememberSnoopingSetting` deliberately
  stores a state equal to the platform default — the "store only departures" rule governs writes made
  through the switch, but here the user asked explicitly, and pinning a default is how you say *keep it
  this way even if the default changes*.

## Battery history (`battery/`)

Fork screen **Battery history / 電池** — per-app drain over time, entered from the battery icon on the main top bar (right of the monitor gauge). Answers what the monitor cannot: *what drained the battery while you weren't looking*. Added +24 after a real investigation (2026-07-29) that found `shiroikuma.jami` sustaining **153 packets/second backgrounded** (~98 MB/h) and, as a result, **deep Doze never engaging once** — only `Device light idling` ever appeared in the dump.

- **The permission is the whole design.** `android.permission.BATTERY_STATS` is `signature|privileged|**development**` (verified on-device 2026-07-29 — same level as `DUMP`), so `SelfPermissions.init()` grants it to us exactly as it already grants `DUMP`. The platform **persists** that grant, so once it lands the sampler reads counters **in-process and survives reboot with no shell alive** — which is what makes unattended sampling viable on a phone whose ADB-over-TCP dies at every reboot. `BatteryStatsReader` tries the in-process binder dump first (`ServiceManager.getService("batterystats")` → `binder.dump(pipe, {"--charged"})`, read on a **separate thread** or the 64 KB pipe deadlocks), falling back to `Runner` only for the window before the grant.
- **LANDMINE — three different CPU numbers, only one is window-scoped.** `Proc <name>: CPU: … usr + … krn` accumulates over the **process lifetime** (a long-lived process shows minutes of CPU inside a 4-minute window — this produced a wrong "19% of a core" answer once); `Total cpu time: u= s=` is the window-scoped field and is what `BatteryStatsParser` reads (barely populated on this device, so the network/wakelock counters carry the ranking). Always establish a rate by **diffing two dumps**, never by reading one.
- **LANDMINE — `--checkin` is NOT the same data.** Its `nt` network counters are **lifetime** totals, reading 5–6× the "Statistics since last charge" section for the same uid. Never mix the two sources. `--checkin` remains the right place for the uid→package map (`9,0,i,uid,<uid>,<pkg>`).
- **LANDMINE — duration regex.** Durations print as `1h 14m 1s 69ms`; a `(\d+)(h|m|s|ms)` alternation matches `69ms` as 69 **minutes**. `ms` must come first. This cost a wrong answer.
- **No mAh anywhere, deliberately.** Huawei's power profile is gutted — the dump reads `Capacity: 5.00`, `Computed drain: 0`, `Estimated battery capacity: 1.00 mAh` — so `BatteryStatsManager`'s per-app mAh is fiction here. The ranking is a composite **"impact"** score (`BatterySampleDao.BatteryAggregate.impactScore()`) over measured counters: wakelock ms + radio-active ms + 1.5× CPU ms + 0.5× sensor ms + 2 ms/packet + 0.1× fg-service ms. Rows ≥25% share render blood red.
- **Storage is deltas, never absolutes.** The platform zeroes every per-uid counter at full charge, so `BatterySampler` diffs consecutive `BatterySnapshot`s and stores the difference (`db/entity/BatterySample`, Room **v8**, migration `M_7_8` — its CREATE TABLE must stay byte-identical to `AppsDb_Impl`'s or the DB refuses to open and takes the whole app with it). Reset detection is `BatterySnapshot.continues()` = same `Start clock time` **and** non-decreasing `Time on battery`; on a reset the absolutes *are* the post-reset usage and get written as one bucket rather than dropped, because the hours around a charge are the ones worth seeing. Per-counter deltas clamp at zero (a dying process shrinks some counters without a full reset). A dump that fails to parse writes **nothing** — an all-zero bucket would read back as a quiet hour that never happened.
- **Sampling is free by construction.** `BatterySamplerJob` is a `setPersisted` periodic `JobScheduler` job (15 min default = JobScheduler's own floor), **no wakelock, no foreground service, no exact alarm** — the counters are cumulative, so a late reading only widens a bucket. `--charged` cuts the dump from 443 KB to 69 KB. A monitor that woke the phone to measure why the phone was awake would be its own worst finding.
- **mAh where it's real, never where it isn't (+25).** The parser now reads the `Estimated power use (mAh)` block: `Capacity: X, Computed drain: Y` plus per-uid `UID u0a954: 394 ( screen=… cpu=… wifi=… )`. **The sanity gate is `Capacity >= 100`** — no phone has a sub-100 mAh battery, so a smaller value means `power_profile.xml` is stubbed (Mate XT: **5.00**). `powerModelUsable` is stored **per bucket**, not assumed globally, so a history spanning several phones (or a ROM update that fixes the profile) can never make old zero-mAh rows read as genuine "used no power". Where usable, the row headline becomes mAh and a "Estimated power (mAh)" sort appears; where not, the sort isn't offered at all and the share-of-impact percentage stands in. ⋮ → *Status* always states which case you're in and why.
- **Open-ended metrics, because it runs on several phones (+25).** Beyond the fixed columns, each bucket carries an `extras` JSON map: per-component mAh (`mah.cpu`, `mah.wifi`, …), job/sync time + counts, process-state times (top/foreground/background/cached), Wi-Fi running/lock/scan, Bluetooth scan, audio/video/camera/flashlight/vibrator, radio wakeup count. Simple `Label: <duration>` counters are **table-driven** (`DURATION_METRICS` in `BatteryStatsParser` — adding one is a single row), and `BatteryMetrics` renders **unknown keys too** (de-underscored, with the unit inferred from an `_ms`/`_count`/`mah.` suffix), so a counter a future Android release starts printing still shows up instead of being dropped. Component sets are never enumerated — they differ per release.
- Prefs: `shiroikuma_battery` (decisions — travels in export, classified `MONITOR`) and `shiroikuma_battery_state` (the previous raw snapshot — in `EXCLUDED_PREFS`, since restoring another phone's counters makes the next delta garbage). Scheduling is kicked from `Ops.setAuthenticated`, `BootReceiver`, and screen open.
- **Control panel, not a dialog (+26).** Tapping a row opens `battery/BatteryAppDetailActivity` — header (tap → App details, snowflake toggles freeze) · **Recommended** · History bars · Controls · Measurements. Long-press keeps the old raw-counter dialog as the quick look. `battery/BatteryAdvisor.java` is the point of the screen: it maps the *dominant counter* to the lever that addresses it (packets → network lever, wakelock ms → `WAKE_LOCK` op, CPU → `RUN_ANY_IN_BACKGROUND`, sensor ms → location, fg-service → `START_FOREGROUND`, holding a Doze exemption while busy → drop it), and **freeze is offered last and only after something already scored HIGH** — a map app burning GPS needs a location lever, not removal. All thresholds are **rates, not totals**, so an app measured over 4 minutes and one over 4 days are judged alike. `battery/BatteryControls.java` is the thin facade over `FreezeUtils` / `PackageManagerCompat` / `SnoopingLevers` / app ops — never grow a second copy of those rules here; in particular freeze goes through `FreezeUtils.freeze`, so the **必要 guard keeps working** and its throw is surfaced as `protected_profile_block`. `setOpAllowed` **re-reads the op after writing** and reports whether the platform complied (`AppOpsService` accepts writes it discards).
- **LANDMINE — frozen apps need the match flags.** A package frozen by *hiding* is invisible to a plain `getApplicationInfo`, so `BatteryUsageViewModel.resolveInfo` and the panel's `gather()` both pass `MATCH_UNINSTALLED_PACKAGES | MATCH_DISABLED_COMPONENTS`. Without them the very apps you froze for draining lose their label and icon and render as a bare package string. Rows show frozen state like the main list (icon at 0.5 alpha + filled ice-blue `ic_snowflake_24dp`), the icon column toggles freeze, and a ✕ force-stops — hidden for frozen rows and package-less uids, where it means nothing.
- **Alerts, comparison, screen-off view (+27).** **Alerts** (`battery/BatteryAlerts.java`, **off by default**) run from `BatterySampler.sample` — the point of background sampling is that the drain happens in a pocket, so the "went rogue" check cannot live on a screen you must remember to open. Judged over a **trailing hour** (`aggregateRange`), never a single bucket, and skipped unless ≥half that hour is actually covered — otherwise the first bucket after a gap is judged as if it were the whole window. Thresholds: packets/s, wakelock % of hour, CPU % of a core; 6 h per-uid cooldown stored in the **state** prefs (device-local: an exported "already warned" would mute the alert on another phone), plus a per-app ignore list for apps you accept as heavy. The notification opens straight into that app's control panel. **Comparison**: `aggregateForUidRange` sums the equally long window immediately before, and the panel compares **rates, not totals** — the earlier window is often shorter (history doesn't reach back yet) and comparing sums would invent an improvement that is only missing data; it is skipped entirely when the previous window is under a quarter as long. Green = down, because every metric here is a cost. **Screen-off view**: `aggregateScreenOff` restricts to buckets whose device row has `screen_on_ms = 0` — every row in one sampling pass shares a `ts`, so the device row is the authority for all of them. Strict on purpose: a bucket where the screen came on at all is contaminated and dropped whole. The toolbar subtitle says when the filter is on, or the smaller numbers read as a bug.
- **Battery list uses the main list's conventions (+30).** `item_battery_card.xml` mirrors `item_main.xml` — `MaterialCardView` + film, icon column carrying the freeze snowflake and the force-stop ✕ under the icon, italic label for frozen rows, type-coloured running box (user yellow / system orange) — and only the right-hand column differs: version/backup/signature is replaced by share-of-drain + bar + the counters behind it. `BatteryUsageAdapter` **shares the conventions, not the code** (the main adapter is bound to `ApplicationItem` and the selection/profile machinery), but reads every colour from the same `ColorPrefs`/`RunningBoxPrefs` keys, so the two screens cannot drift apart; `reloadColors()` runs from `onResume`. Column layout via `BatteryLayoutPrefs` + the same 3×3 toolbar icon. **Both grid icons are `showAsAction="always"`** — as `ifRoom` they silently fell into the overflow on a narrow panel, which is where 白い熊 kept finding the main one.
- **Battery screen header (+30).** Fixed panel above the list, about two rows tall: left `BatteryLevelView` (device level trace, voltage as a fainter second trace scaled to its own visible range, **charging stretches as a red band** — a discharge chart that silently merges charging shows a line going *up* and the reader stops trusting all of it), opening on the last 24 h with the full retained history reachable by dragging left, pinch-zoom + double-tap-fit; right `BatteryTopDrainersView` (last **2 h**, up to 5 colour columns with percentages — "what is eating it right now" is a different question from "what ate it today"). Needs `voltage_mv` + `charging` on the device row (Room **v10**, `M_9_10`), read from the sticky `ACTION_BATTERY_CHANGED` — voltage has no `BATTERY_PROPERTY_*` constant and the sticky intent needs no privileges.
- **History chart is a real time axis, not an index axis (+29).** `battery/BatteryHistoryView.java` places and *sizes* each bar by its own `[ts - duration, ts)`. **This is the point of it:** buckets are not uniform — Doze defers the sampler, so an overnight bucket can be hours wide while a daytime one is 15 minutes — and an index-based chart draws those as equals, erasing exactly the idle gaps you are investigating. Pinch zooms (focus-preserving), drag pans, double-tap fits, tap selects a bar and the caption becomes the readout (its real window + bucket length). The vertical scale is the max of the **visible** bars, so zooming into a quiet stretch reveals its shape instead of leaving it flat under one distant spike. Day boundaries draw as brighter delimiters with date labels; a finer tick ladder (1m…1d, chosen for ≤8 ticks) draws underneath with clock labels, all aligned to *local* wall-clock via `Calendar`. **LANDMINE — the chart lives inside a `NestedScrollView`:** without `getParent().requestDisallowInterceptTouchEvent(true)` on ACTION_DOWN the first vertical wobble of a pan hands the gesture to the scroller and the chart never sees the rest of it; and the scroll detector must be skipped while `ScaleGestureDetector.isInProgress()` or pinch and pan fight.
- **LANDMINE — `SnoopingLever.stateLabelRes` returns 0 meaning "use the generic label", not "no label".** Passing it straight to `getString` throws `Resources$NotFoundException: String resource ID #0x0` — this crashed the whole control panel in +27 (the network lever names only its FOREGROUND rung, so ALLOWED/BLOCKED returned 0). Any caller must mirror `AppDetailsSnoopingFragment`'s fallback to `snooping_state_allowed`/`_blocked`/`_foreground`; `BatteryAppDetailActivity.stateLabel()` does. **Build-pipeline lesson from the same fix:** the hard gate only checks that the server JARs are non-empty, so when the Gradle daemon died mid-build the script happily signed the *previous* build's leftover unsigned APK under the new version name. **Always confirm `BUILD SUCCESSFUL` before signing**, and if in doubt compare the compiled `.class` mtime against the edited source.

### Doze on the Mate XT (measured 2026-07-29)

`dumpsys deviceidle` reports `mDeepEnabled=true`, `mLightEnabled=true` — **AOSP Doze is fully enabled**, and it is *not* PowerGenie (Huawei's own freezer, which 白い熊 has disabled; the two are unrelated mechanisms). Timings are stock: `inactive_to=30m`, `idle_after_inactive_to=30m`, `sensing_to=4m`, `locating_to=30s` — so deep idle needs roughly an hour of **uninterrupted** screen-off before it can engage, and any screen-on resets the walk. **`mUseMotionSensor=true` but `mMotionSensor=null`** — the device exposes accelerometers and a step detector but **no wake-up significant-motion sensor**, so the controller never binds one; whether that blocks deep idle or merely defers it to the 4-minute `sensing_to` timeout is not answerable from a dump. **Do not conclude "deep Doze never engages here" from a short window** — a 74-minute cycle with 27 minutes of screen-on could never have reached it regardless, and an earlier session wrongly called its absence a smoking gun. The battery screen records `Device full idling` per bucket, so an overnight run answers it properly; `dumpsys deviceidle force-idle` (screen off, then `unforce`) settles it immediately.

## Process monitor / reaper (`processreaper/`)

Fork replacement for the legacy "Running apps" screen, now **deleted** (`RunningAppsActivity`/`Adapter`/`ViewModel`/`RunningAppDetails`, their layouts/menus, the manifest + `activity_main_actions` entries, and `Prefs.RunningApps`). The **shared** enumeration infra it relied on stays — `runningapps/ProcessParser`, `ProcessItem`, `AppProcessItem` (the monitor uses these). The two now-dead `PREF_RUNNING_APPS_*` keys are kept in the `AppPref` enum with inlined int defaults (0) to avoid touching the persisted enum's ordering. Entry point: the standalone gauge icon (`drawable/ic_monitor.xml`, custom `actionLayout` `view_toolbar_monitor.xml`) left of the filter icon on the main top bar; long-pressing the monitor's overflow opens the 白い熊 応用管理 UI page (same `attachOverflowLongPress` trick as MainActivity).

- **Enumeration** reuses `runningapps/ProcessParser` (made callable via the new `public static getRunningProcessList()`). Live **instantaneous CPU%** is NOT from `ProcessItem` — its `cpuTimeConsumed` is truncated to whole seconds (`Ps.java` divides ticks by CLK_TCK). The monitor samples raw `utime+stime` ticks itself via `Runner.runCommand("cat /proc/[0-9]*/stat …")` and diffs across refreshes (`ProcessMonitorViewModel.sampleCpuTicks`). **Memory ranks by PSS, not RSS** (`samplePss`): RSS double-counts shared pages, but killing a process frees roughly its *unique* footprint = PSS, so PSS is the right number for a reaper. **LANDMINE:** non-root shell **cannot** read `/proc/<pid>/smaps_rollup` (ptrace-gated → `EPERM` cross-process; only ~8 of ~787 pids, all shell-owned, are readable) — verified on-device, so the cheap `/proc` path is dead. The only source is `dumpsys meminfo`'s "Total PSS by process" section (`<kB>K: name (pid N …)`), parsed pid→bytes and **cached `PSS_TTL_MS` (15 s)** because that dumpsys is heavy and memory moves slowly (vs. the 2 s CPU tick). `memBytesFor(p)` returns PSS when known, else falls back to `p.getMemory()` (RSS) — used for both the displayed size and the sort key in all three row builders (`singleRow`/`sharedRow`/`leakRow`).
- **`ProcessClassifier`** = PROTECTED vs KILLABLE. **LANDMINE:** `ProcessParser` resolves uid 2000 to its owning package `com.android.shell`, so every shell process (incl. orphaned `logcat`) arrives as an `AppProcessItem` — gate leak/shell logic on the **kill method** (`METHOD_SIGKILL` = shell-owned), NEVER on `instanceof AppProcessItem`. Smart kill router: app package → `PackageManagerCompat.forceStopPackage`; package-less shell pid → `kill -9 <pid>` (shell can signal its own uid; the legacy screen wrongly gated this on root). Built-in denylist (Tasker/Shizuku/self/IME/system…) + **user-editable** protected set (`ReaperPrefs`, tap-Protect/Allow); the privilege chain (our own `am.jar`/`main.jar` server, Shizuku) is hard-protected so the reaper can't sever its own kill ability. The **built-in denylist is itself user-overridable** (`ReaperPrefs` `allowed_packages`): **long-press** a built-in-protected app (e.g. Huawei Home) → "Allow killing" makes it killable; long-press again → "Restore protection". `ProcessClassifier.isOverridableDenylist(pkg)` (= in `DENYLIST` && NOT a `SHELL_PROTECT_SUBSTR` match) gates this — the privilege chain (shizuku/am/self) can never be overridden. The adapter routes long-press to the override toggle for these apps (instead of multi-select) and hides their Protect button; `classify`'s denylist check skips protection when the pkg is in the allowed set and not privilege-chain. The foreground launcher still shows "in use" while it's on screen, so kill it from inside the monitor (launcher backgrounded). **LANDMINE — our own command shells:** `Runner` pipes every command (including the kill) through a long-lived `sh` spawned by the `:priv:0` server, plus transient `sh -c` helpers per command (each refresh runs several dumpsys/cat). These arrive as bare `sh` tagged `com.android.shell` (uid 2000) — the cmdline-substring guard misses them, so they were mis-grouped as a killable **"sh ×N" leak**; tapping it tried to `kill -9` the very shell running the kill and failed with "Couldn't kill". Fixed by three layers: (1) **ancestry protection** (`ProcessClassifier.ancestryProtectedPids`) walks each pid's `PPid` chain (harvested for free from the same `/proc/*/stat` batch — field 1 after `comm` — into `mPpid`) and protects (`"privilege"`) anything descending from our roots; genuine orphaned leaks (reparented to init) are NOT descendants and stay killable. (2) **LANDMINE — root detection can't use `ProcessParser`:** the `:priv:0` server runs as **uid 2000** with **`comm` = "main"**, is **reparented to init**, and `ProcessParser`'s name/cmdline fields don't expose our package for it — so the server was never flagged as a root and the walk `sh → main(:priv:0) → init` hit nothing. Roots are read straight from `/proc/*/cmdline` via `grepOurRootPids()` (`grep -la -e <pkg> -e shizuku -e am_local_server /proc/[0-9]*/cmdline`). **The chain is INVERTED from the obvious guess:** the ADB-mode tree is `am_local_server (uid 2000, comm "main", reparented to init) → sh → sh → shiroikuma.oyokanri:priv:0`, i.e. the package-bearing `:priv:0` is the **leaf** and the two helper `sh` are its **ancestors** — so a pure descendant-closure from the `:priv:0` root never reaches them. Two cover it: (a) the grep also matches `am_local_server` (the true top of the chain) so its whole subtree closes downward; (b) `ancestryProtectedPids` also walks **UP** via PPid from each **uid-2000** root, adding ancestors until init (pid ≤ 1) — never from the app / shizuku-api (uid ≥ 10000, zygote children — walking up would hit the shared zygote and over-protect everything). (3) **Liveness filter:** the monitor's own pipeline (`ps`, `cat`, `sed`, `sh` — all names in `TRANSIENT`) spawns helpers that land in the enumeration then die ms later, masquerading as a leak. `load()` now enumerates FIRST, reads `/proc/*/stat` AFTER, and drops any pid absent from that later stat read (ghosts gone; the persistent server shell that survives is caught by ancestry). Also, SIGKILL **reports by whether the kill was permitted, not by exit code or a liveness probe** (`doKill`): `kill -9` returns non-zero if any listed pid already exited (ESRCH), and — the subtler trap — it returns *before* the kernel finishes teardown, so an immediate `[ -d /proc/$p ]` race-catches a dying/zombie entry and reports a false "Couldn't kill" even though the row vanished. For a same-uid SIGKILL the only true failure is **EPERM**, so `doKill` runs `kill -9 <pids> 2>&1` and fails only if the output contains "operation not permitted"/"permission denied"; ESRCH ("No such process") and silent success both count as killed. **Actively-in-use protection** (reason `"in use"`): the foreground/top app(s) and any process hosting a live **foreground service** (media/nav/recorder/sync) are protected so you can't one-tap kill what's on screen or playing. Detected in `ProcessMonitorViewModel.gatherActivePackages()` by parsing `dumpsys activity services` (ServiceRecord blocks carrying `isForeground=true`) and `dumpsys activity activities` (every `ResumedActivity` line — plural on the foldable in split-screen), unioned into a package set passed to `classify(...)`. The set is **cached `ACTIVE_TTL_MS` (5 s)** because the two dumpsys parses are heavier than the per-tick `/proc` read and foreground state changes slowly; best-effort, so a parse miss just drops back to the prior (less-protective) behaviour, never a crash. These rows render grey (`MONITOR_PROTECTED`) with no Kill/Protect button — no adapter change was needed.
- **Leak grouping** clusters identical package-less shell commands into one "comm ×N — LEAK" row (multi-pid `kill -9`); leaks are **pinned to the top** of the sort (they're tiny and would otherwise sink). The cluster size is the **configurable** `MonitorPrefs.getLeakThreshold` (default 3, min 2, max 10; known-transient comms in `TRANSIENT` floor at 2). An optional **min-age** filter (`getLeakMinAgeSec`, default 0 = off) only flags a cluster once its **oldest** member has lived that long — so a momentary burst isn't flagged; age is `elapsedRealtime − starttime/CLK_TCK`, with `starttime` (proc stat field 22 → `mStart`) harvested from the same `/proc/*/stat` batch as ppid. Shared processes (one pid, many packages, e.g. `system_server`) dedupe into one row. **Multi-process apps collapse by package** (`appRow`): a browser's main + `:tab`/`:gpu` children (same package, uid ≥ 10000, not shell) become ONE row summing RAM/CPU with all pids — force-stop kills the whole package anyway, so N near-identical rows were just noise (`isAppGroupable` gates it; single-process apps still go through `singleRow`). Toolbar subtitle shows "N processes · M killable · L leaks". A **toolbar SearchView** (`action_monitor_search`, themed yellow-on-black) filters the live list by app label / process name / package (`ProcessMonitorViewModel.setQuery` → `filterRows` over the cached `mAllRows`); the query survives the 2 s auto-refresh because every load re-applies it. (Search is the way to find a specific app like the launcher, which sinks low in the PSS-sorted list.) **Tap a row opens the dedicated `ProcessDetailActivity`** (a full screen, not the kill dialog — kill is the per-row ✕ button or the detail's "Kill" toolbar action). It's launched with the cheap fields as Intent extras (pid, pids[], pkg, title, killable, method, uid, reason, user, cpu, pss, in-use) and gathers the rest fresh for its one pid via a single privileged read of `/proc/<pid>/{status,stat,oom_score_adj,oom_score,attr/current,cgroup,cmdline,fd}` (marker-delimited `@ST@`/`@SS@`/… sections, parsed in `gather()`), plus app metadata from the PackageManager. Sections: Process · Memory (PSS/RSS/peak/virtual/data/stack/swap/FDs) · CPU & scheduling (CPU%/CPU time/priority/nice/policy/ctxt switches) · Lifecycle & security (oom_score_adj/oom_score/in-use/age/tracer/seccomp/SELinux/cgroup) · App (label/version/SDKs/system/debuggable/install dates/paths) · Classification. Values render as a two-column label→value list, **selectable** (copyable). A tappable **app icon header** sits at the top (`addIconHeader`, `ImageLoader`) — icon on the left with the app label (large) + package id (smaller) stacked to its right; tap the header to jump into `AppDetailsActivity`. Toolbar: App details (→ `AppDetailsActivity`, real apps only), Kill, Refresh. Must be in `AppearanceUtils.isYellowOnBlackActivity()` + a manifest `<activity>` with `AppTheme.YellowOnBlack`. Long-press still does override/multi-select; the per-row buttons still Protect/Kill. **The whole detail page is settable** in the 白い熊 応用管理 UI "Process detail page" group: header **icon size** + **line padding** sliders (`MonitorPrefs.getDetailIconDp`/`getDetailRowPadDp`), plus the five text surfaces (app label, app ID, section header, field label, field value) each with full font attrs via the data-driven `FontPrefs`/`FontUtil.apply` system (family + weight + size) + colour (`ColorPrefs.MONITOR_DETAIL_*`). `ProcessDetailActivity` sets factory defaults then `FontUtil.apply(tv, FontPrefs.MONITOR_DETAIL_*)` (size 0/weight 0/family "" = inherit, so DEFAULT cascades). A **faceted filter** (toolbar funnel `action_monitor_filter`) narrows the list across two AND-ed dimensions — killability {Killable, Protected, **Togglable**} × type {User, System, Shell, Leaks} (`ProcessMonitorViewModel.setFilter(killMask, typeMask)` + `typeOf(row)` + `killBits(row)`; combined with the search query in `filterRows`). The killability facets **OR-combine** (`killBits` is a bitmask): a **Togglable** row is protected *now* but user-flippable to killable (`isTogglable` = reason `"you"` OR `isOverridableDenylist`), and it also carries `F_PROTECTED`, so **Killable + Togglable = everything that can ultimately be killed**. Session-only multi-choice dialog; nothing checked in a dimension = unconstrained.
- **Prefs / UI** (all in the `pref_monitor_*` "Process monitor" group on the UI page; live via per-bind reads + `onResume` separator reload): columns — adaptive (default, the 450dp auto-fit grid) or a fixed 1–4, held in `MonitorPrefs` and picked from the **same single-choice dialog as the main list** (`ProcessMonitorActivity.showLayoutPicker`/`applyListLayout`, mirroring `MainActivity`; the top-bar grid icon used to cycle blind, which showed neither the options nor the current one) — app-icon size, row vertical padding, **leak threshold + leak min-age** sliders, four row-state colours (`ColorPrefs.MONITOR_KILLABLE/LEAK/PROTECTED/USER_PROTECTED`), and the separator grid (`MonitorSeparatorPrefs` + `ColorPrefs.MONITOR_SEPARATOR_H/V`, drawn by `MonitorSeparatorDecoration` — a copy of `MainSeparatorDecoration` that also draws a top line on the first row).
- **Dialogs LANDMINE:** `DynamicColors.applyToActivityIfAvailable` (in `AppearanceUtils`, run after `setTheme`) clobbers the activity's `materialAlertDialogTheme`, AND `MaterialAlertDialogBuilder.create()` overrides the window background with its own borderless `MaterialShapeDrawable`. So themed dialogs must (a) pass `R.style.ThemeOverlay_AppTheme_MaterialAlertDialog_YellowOnBlack` **explicitly** to the builder (for yellow text/radio), and (b) set the bordered drawable on the **window background after `show()`** (`presentWithYellowBorder`) — theme attrs alone won't paint the border. The yellow-on-black dialog overlay now also pins `colorControlActivated` (selected radio) and a 2dp border stroke. Any new fork screen must be added to `AppearanceUtils.isYellowOnBlackActivity()` or it gets the dynamic theme.
