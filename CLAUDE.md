## Build & deploy pipeline

**Always build after changes.** Whenever you finish a set of working-tree edits (Java/XML/resources), run the full pipeline below to completion — bump, assemble, sign, verify, copy the signed APK to `~/tmp/` — without waiting for the user to say "Build". Treat a task as unfinished until it has produced a fresh signed APK on disk. If the build fails, stop and surface the error rather than reporting the change as done.

**Always ask how to deliver, after every build.** Delivery of the signed APK is never automatic. After every successful build, summarise what was built and ask **via the `AskUserQuestion` tool** how to deliver it, offering two options in this order: **scp to skhw** (the first / recommended choice → run the `scp` skill) and **adb push to the device** (`adb push /tmp/am-signed.apk /sdcard/tmp/<apk_name>`, needs the phone connected with USB debugging). The tool also lets the user pick "Other" (e.g. neither). Never deliver without asking, and never silently skip the question. Deliver only the chosen way, only once the user answers.

Output APK is named `shiroikuma-oyokanri_${customBaseVersionName}+${customBuildNumber}_arm64-v8a.apk`, derived from `gradle.properties`. Always copy the signed APK to `~/tmp/` before pushing to the device, so a record stays on disk.

```bash
# from repo root
export JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64
export PATH="$JAVA_HOME/bin:$PATH"
export ANDROID_HOME=$HOME/android-sdk

tools/bump-build.sh                            # increments customBuildNumber
echo "sdk.dir=$ANDROID_HOME" > local.properties

./gradlew clean
# Filter benign output on BOTH streams; preserve the exit code with pipefail.
set -o pipefail
./gradlew :app:assembleRelease \
    2> >(grep -vE 'ノート:|Note:|\[CXX5304\]' >&2) \
  | grep -vE 'ノート:|Note:|\[CXX5304\]'

UNSIGNED_APK=$(find app/build/outputs/apk/release -name '*-unsigned.apk' | head -1)

# HARD GATE: the embedded server JARs must be present AND non-empty, or ADB mode
# is dead on arrival (see "Server JARs" note below). Refuse to sign otherwise.
for j in assets/am.jar assets/main.jar; do
    sz=$(unzip -p "$UNSIGNED_APK" "$j" 2>/dev/null | wc -c)
    [ "$sz" -gt 0 ] || { echo "FATAL: $j is empty/missing in APK — refusing to ship"; exit 1; }
done

zipalign -p -f 4 "$UNSIGNED_APK" /tmp/am-aligned.apk
apksigner sign --ks ~/.android-keystores/appmanager-custom.jks \
    --ks-key-alias appmanager \
    --ks-pass pass:appmanager123 \
    --key-pass pass:appmanager123 \
    --out /tmp/am-signed.apk /tmp/am-aligned.apk
apksigner verify --verbose /tmp/am-signed.apk 2>&1 | grep -v 'not protected by signature'

VER=$(grep '^customBaseVersionName=' gradle.properties | cut -d= -f2)
NUM=$(grep '^customBuildNumber='     gradle.properties | cut -d= -f2)
apk_name="shiroikuma-oyokanri_${VER}+${NUM}_arm64-v8a.apk"
cp /tmp/am-signed.apk ~/tmp/"$apk_name"

# After the user has connected the phone with USB debugging:
adb push /tmp/am-signed.apk "/sdcard/tmp/$apk_name"
```

Filter notes:
- `ノート:` / `Note:` are mandatory `javac` summary notes for deprecation/unchecked usage; `-Xlint:none` and `-nowarn` do not suppress them.
- `[CXX5304]` is a benign SDK-XML version-skew message from the NDK pipeline. Brackets must be escaped (`\[CXX5304\]`) for `grep -E`.

**Server JARs (`assets/am.jar` + `main.jar`) — the ADB-mode landmine.** Both are
gitignored and regenerated every build by `:server:create<Variant>ServerJars`
(server/build.gradle), which `d8`-compiles them straight into `app/src/main/assets/`.
`main.jar` is the bootstrap the ADB shell runs to launch AppManager's server; an
empty/missing one makes **ADB mode hang on init then fall back to no-root** (build
+79 shipped a **0-byte main.jar** this way and looked like a code regression — it
was a build race). Two structural guards now prevent it, plus the gate above:
1. **Ordering** — `app/build.gradle` makes `merge<Variant>Assets dependsOn
   :server:create<Variant>ServerJars` via a plain `tasks.matching` edge (the old
   `applicationVariants.mergeAssetsProvider` edge was unreliable under the
   configuration cache — that's how +79 slipped through).
2. **Atomic writes** — server/build.gradle `d8`s each JAR into a **per-variant**
   `server/build/serverjars-tmp/<buildType>/` dir (temp name must keep the `.jar`
   suffix — d8 rejects others; per-variant because release+debug jar tasks run in
   parallel and share nothing), then `Files.move`s it into `assets/`, so a racing
   consumer sees a whole JAR or none, never a partial. Diagnose a suspected recurrence
   with `unzip -p <apk> assets/main.jar | wc -c` (compare a known-good vs bad APK).

## Push workflow

When the user says **"Push"**:
1. `git add -A` (include new files).
2. Show `git status` for the user to review.
3. `git commit -m "<concise imperative title>" -m "<multi-line body describing what changed and why>"`.
4. `git push origin custom` — **never force-push**.
5. Report the resulting commit hash and a one-line summary.

## Translation workflow

The user supplies an English label plus its Japanese translation and where they see it. Procedure:
1. Find the matching string-resource name in `app/src/main/res/values/strings.xml` (e.g. "Frozen apps" → `name="filter_frozen_apps"`).
2. Add `<string name="…">…</string>` to `app/src/main/res/values-ja/strings.xml` under the marker `<!-- Fork: user-supplied Japanese translations -->`.
3. The translation applies wherever that resource is referenced, including the toolbar (via `MainToolbarPrefs.titleForKey`).

## Protected profile (`必要`)

Any app that is a member of an apps profile named **`必要`** is hard-blocked from being frozen and uninstalled. Enforcement sits at the two low-level chokepoints, so no UI path (single-app, batch, profile application, future code) can bypass it.

| Chokepoint | Behaviour |
|---|---|
| `FreezeUtils.freeze(pkg, userId, type)` | Throws `RemoteException` for protected packages. The 2-arg `freeze` delegates to this; all freeze methods (disable/suspend/hide) run after the guard. |
| `PackageInstallerCompat.uninstall(pkg, userId, keepData)` | Returns `false` at the very top, before any work or accessibility dialog. |
| `profiles/ProtectedAppsProfile.java` | Helper. `getProtectedPackages()` unions `packages` from every apps-profile named `必要`. 3 s TTL cache. **Fails open** (a stuck block is worse than briefly missing protection). Call `invalidate()` after profile changes. |

Concrete refusal messages fire at four entry points — the main-list freeze icon, app-details freeze, app-details uninstall, and batch freeze/uninstall — using `R.string.protected_profile_block` (single, `%s` = label) and `R.string.protected_profile_block_multiple` (list, `%s` = names joined with `、`).

## Process monitor / reaper (`processreaper/`)

Fork replacement for the legacy "Running apps" screen, now **deleted** (`RunningAppsActivity`/`Adapter`/`ViewModel`/`RunningAppDetails`, their layouts/menus, the manifest + `activity_main_actions` entries, and `Prefs.RunningApps`). The **shared** enumeration infra it relied on stays — `runningapps/ProcessParser`, `ProcessItem`, `AppProcessItem` (the monitor uses these). The two now-dead `PREF_RUNNING_APPS_*` keys are kept in the `AppPref` enum with inlined int defaults (0) to avoid touching the persisted enum's ordering. Entry point: the standalone gauge icon (`drawable/ic_monitor.xml`, custom `actionLayout` `view_toolbar_monitor.xml`) left of the filter icon on the main top bar; long-pressing the monitor's overflow opens the 白い熊 応用管理 UI page (same `attachOverflowLongPress` trick as MainActivity).

- **Enumeration** reuses `runningapps/ProcessParser` (made callable via the new `public static getRunningProcessList()`). Live **instantaneous CPU%** is NOT from `ProcessItem` — its `cpuTimeConsumed` is truncated to whole seconds (`Ps.java` divides ticks by CLK_TCK). The monitor samples raw `utime+stime` ticks itself via `Runner.runCommand("cat /proc/[0-9]*/stat …")` and diffs across refreshes (`ProcessMonitorViewModel.sampleCpuTicks`). **Memory ranks by PSS, not RSS** (`samplePss`): RSS double-counts shared pages, but killing a process frees roughly its *unique* footprint = PSS, so PSS is the right number for a reaper. **LANDMINE:** non-root shell **cannot** read `/proc/<pid>/smaps_rollup` (ptrace-gated → `EPERM` cross-process; only ~8 of ~787 pids, all shell-owned, are readable) — verified on-device, so the cheap `/proc` path is dead. The only source is `dumpsys meminfo`'s "Total PSS by process" section (`<kB>K: name (pid N …)`), parsed pid→bytes and **cached `PSS_TTL_MS` (15 s)** because that dumpsys is heavy and memory moves slowly (vs. the 2 s CPU tick). `memBytesFor(p)` returns PSS when known, else falls back to `p.getMemory()` (RSS) — used for both the displayed size and the sort key in all three row builders (`singleRow`/`sharedRow`/`leakRow`).
- **`ProcessClassifier`** = PROTECTED vs KILLABLE. **LANDMINE:** `ProcessParser` resolves uid 2000 to its owning package `com.android.shell`, so every shell process (incl. orphaned `logcat`) arrives as an `AppProcessItem` — gate leak/shell logic on the **kill method** (`METHOD_SIGKILL` = shell-owned), NEVER on `instanceof AppProcessItem`. Smart kill router: app package → `PackageManagerCompat.forceStopPackage`; package-less shell pid → `kill -9 <pid>` (shell can signal its own uid; the legacy screen wrongly gated this on root). Built-in denylist (Tasker/Shizuku/self/IME/system…) + **user-editable** protected set (`ReaperPrefs`, tap-Protect/Allow); the privilege chain (our own `am.jar`/`main.jar` server, Shizuku) is hard-protected so the reaper can't sever its own kill ability. The **built-in denylist is itself user-overridable** (`ReaperPrefs` `allowed_packages`): **long-press** a built-in-protected app (e.g. Huawei Home) → "Allow killing" makes it killable; long-press again → "Restore protection". `ProcessClassifier.isOverridableDenylist(pkg)` (= in `DENYLIST` && NOT a `SHELL_PROTECT_SUBSTR` match) gates this — the privilege chain (shizuku/am/self) can never be overridden. The adapter routes long-press to the override toggle for these apps (instead of multi-select) and hides their Protect button; `classify`'s denylist check skips protection when the pkg is in the allowed set and not privilege-chain. The foreground launcher still shows "in use" while it's on screen, so kill it from inside the monitor (launcher backgrounded). **LANDMINE — our own command shells:** `Runner` pipes every command (including the kill) through a long-lived `sh` spawned by the `:priv:0` server, plus transient `sh -c` helpers per command (each refresh runs several dumpsys/cat). These arrive as bare `sh` tagged `com.android.shell` (uid 2000) — the cmdline-substring guard misses them, so they were mis-grouped as a killable **"sh ×N" leak**; tapping it tried to `kill -9` the very shell running the kill and failed with "Couldn't kill". Fixed by three layers: (1) **ancestry protection** (`ProcessClassifier.ancestryProtectedPids`) walks each pid's `PPid` chain (harvested for free from the same `/proc/*/stat` batch — field 1 after `comm` — into `mPpid`) and protects (`"privilege"`) anything descending from our roots; genuine orphaned leaks (reparented to init) are NOT descendants and stay killable. (2) **LANDMINE — root detection can't use `ProcessParser`:** the `:priv:0` server runs as **uid 2000** with **`comm` = "main"**, is **reparented to init**, and `ProcessParser`'s name/cmdline fields don't expose our package for it — so the server was never flagged as a root and the walk `sh → main(:priv:0) → init` hit nothing. Roots are read straight from `/proc/*/cmdline` via `grepOurRootPids()` (`grep -la -e <pkg> -e shizuku -e am_local_server /proc/[0-9]*/cmdline`). **The chain is INVERTED from the obvious guess:** the ADB-mode tree is `am_local_server (uid 2000, comm "main", reparented to init) → sh → sh → shiroikuma.oyokanri:priv:0`, i.e. the package-bearing `:priv:0` is the **leaf** and the two helper `sh` are its **ancestors** — so a pure descendant-closure from the `:priv:0` root never reaches them. Two cover it: (a) the grep also matches `am_local_server` (the true top of the chain) so its whole subtree closes downward; (b) `ancestryProtectedPids` also walks **UP** via PPid from each **uid-2000** root, adding ancestors until init (pid ≤ 1) — never from the app / shizuku-api (uid ≥ 10000, zygote children — walking up would hit the shared zygote and over-protect everything). (3) **Liveness filter:** the monitor's own pipeline (`ps`, `cat`, `sed`, `sh` — all names in `TRANSIENT`) spawns helpers that land in the enumeration then die ms later, masquerading as a leak. `load()` now enumerates FIRST, reads `/proc/*/stat` AFTER, and drops any pid absent from that later stat read (ghosts gone; the persistent server shell that survives is caught by ancestry). Also, SIGKILL **reports by whether the kill was permitted, not by exit code or a liveness probe** (`doKill`): `kill -9` returns non-zero if any listed pid already exited (ESRCH), and — the subtler trap — it returns *before* the kernel finishes teardown, so an immediate `[ -d /proc/$p ]` race-catches a dying/zombie entry and reports a false "Couldn't kill" even though the row vanished. For a same-uid SIGKILL the only true failure is **EPERM**, so `doKill` runs `kill -9 <pids> 2>&1` and fails only if the output contains "operation not permitted"/"permission denied"; ESRCH ("No such process") and silent success both count as killed. **Actively-in-use protection** (reason `"in use"`): the foreground/top app(s) and any process hosting a live **foreground service** (media/nav/recorder/sync) are protected so you can't one-tap kill what's on screen or playing. Detected in `ProcessMonitorViewModel.gatherActivePackages()` by parsing `dumpsys activity services` (ServiceRecord blocks carrying `isForeground=true`) and `dumpsys activity activities` (every `ResumedActivity` line — plural on the foldable in split-screen), unioned into a package set passed to `classify(...)`. The set is **cached `ACTIVE_TTL_MS` (5 s)** because the two dumpsys parses are heavier than the per-tick `/proc` read and foreground state changes slowly; best-effort, so a parse miss just drops back to the prior (less-protective) behaviour, never a crash. These rows render grey (`MONITOR_PROTECTED`) with no Kill/Protect button — no adapter change was needed.
- **Leak grouping** clusters identical package-less shell commands into one "comm ×N — LEAK" row (multi-pid `kill -9`); leaks are **pinned to the top** of the sort (they're tiny and would otherwise sink). The cluster size is the **configurable** `MonitorPrefs.getLeakThreshold` (default 3, min 2, max 10; known-transient comms in `TRANSIENT` floor at 2). An optional **min-age** filter (`getLeakMinAgeSec`, default 0 = off) only flags a cluster once its **oldest** member has lived that long — so a momentary burst isn't flagged; age is `elapsedRealtime − starttime/CLK_TCK`, with `starttime` (proc stat field 22 → `mStart`) harvested from the same `/proc/*/stat` batch as ppid. Shared processes (one pid, many packages, e.g. `system_server`) dedupe into one row. **Multi-process apps collapse by package** (`appRow`): a browser's main + `:tab`/`:gpu` children (same package, uid ≥ 10000, not shell) become ONE row summing RAM/CPU with all pids — force-stop kills the whole package anyway, so N near-identical rows were just noise (`isAppGroupable` gates it; single-process apps still go through `singleRow`). Toolbar subtitle shows "N processes · M killable · L leaks". A **toolbar SearchView** (`action_monitor_search`, themed yellow-on-black) filters the live list by app label / process name / package (`ProcessMonitorViewModel.setQuery` → `filterRows` over the cached `mAllRows`); the query survives the 2 s auto-refresh because every load re-applies it. (Search is the way to find a specific app like the launcher, which sinks low in the PSS-sorted list.) **Tap a row opens the dedicated `ProcessDetailActivity`** (a full screen, not the kill dialog — kill is the per-row ✕ button or the detail's "Kill" toolbar action). It's launched with the cheap fields as Intent extras (pid, pids[], pkg, title, killable, method, uid, reason, user, cpu, pss, in-use) and gathers the rest fresh for its one pid via a single privileged read of `/proc/<pid>/{status,stat,oom_score_adj,oom_score,attr/current,cgroup,cmdline,fd}` (marker-delimited `@ST@`/`@SS@`/… sections, parsed in `gather()`), plus app metadata from the PackageManager. Sections: Process · Memory (PSS/RSS/peak/virtual/data/stack/swap/FDs) · CPU & scheduling (CPU%/CPU time/priority/nice/policy/ctxt switches) · Lifecycle & security (oom_score_adj/oom_score/in-use/age/tracer/seccomp/SELinux/cgroup) · App (label/version/SDKs/system/debuggable/install dates/paths) · Classification. Values render as a two-column label→value list, **selectable** (copyable). A tappable **app icon header** sits at the top (`addIconHeader`, `ImageLoader`) — icon on the left with the app label (large) + package id (smaller) stacked to its right; tap the header to jump into `AppDetailsActivity`. Toolbar: App details (→ `AppDetailsActivity`, real apps only), Kill, Refresh. Must be in `AppearanceUtils.isYellowOnBlackActivity()` + a manifest `<activity>` with `AppTheme.YellowOnBlack`. Long-press still does override/multi-select; the per-row buttons still Protect/Kill. **The whole detail page is settable** in the 白い熊 応用管理 UI "Process detail page" group: header **icon size** + **line padding** sliders (`MonitorPrefs.getDetailIconDp`/`getDetailRowPadDp`), plus the five text surfaces (app label, app ID, section header, field label, field value) each with full font attrs via the data-driven `FontPrefs`/`FontUtil.apply` system (family + weight + size) + colour (`ColorPrefs.MONITOR_DETAIL_*`). `ProcessDetailActivity` sets factory defaults then `FontUtil.apply(tv, FontPrefs.MONITOR_DETAIL_*)` (size 0/weight 0/family "" = inherit, so DEFAULT cascades). A **faceted filter** (toolbar funnel `action_monitor_filter`) narrows the list across two AND-ed dimensions — killability {Killable, Protected, **Togglable**} × type {User, System, Shell, Leaks} (`ProcessMonitorViewModel.setFilter(killMask, typeMask)` + `typeOf(row)` + `killBits(row)`; combined with the search query in `filterRows`). The killability facets **OR-combine** (`killBits` is a bitmask): a **Togglable** row is protected *now* but user-flippable to killable (`isTogglable` = reason `"you"` OR `isOverridableDenylist`), and it also carries `F_PROTECTED`, so **Killable + Togglable = everything that can ultimately be killed**. Session-only multi-choice dialog; nothing checked in a dimension = unconstrained.
- **Prefs / UI** (all in the `pref_monitor_*` "Process monitor" group on the UI page; live via per-bind reads + `onResume` separator reload): columns 1/2/3 (`MonitorPrefs`, top-bar grid toggle), app-icon size, row vertical padding, **leak threshold + leak min-age** sliders, four row-state colours (`ColorPrefs.MONITOR_KILLABLE/LEAK/PROTECTED/USER_PROTECTED`), and the separator grid (`MonitorSeparatorPrefs` + `ColorPrefs.MONITOR_SEPARATOR_H/V`, drawn by `MonitorSeparatorDecoration` — a copy of `MainSeparatorDecoration` that also draws a top line on the first row).

## Workflow notes for Claude Code (vs. the earlier Claude.ai sessions)

The skill file `.claude/skills/appmanager-fork/SKILL.md` describes a fork-development history that ran inside Claude.ai with a paste-ready patch workflow ("emit a patch → user applies → user says Push → finalize hash"). **In Claude Code that workflow no longer applies** — you have direct file-edit, bash, and git tools. So:

- Edit files in the working tree directly. Don't generate patch files unless the user explicitly asks for one.
- Don't generate paste-ready shell blocks (cyan echo prefixes, yellow gates, etc.); run the commands yourself.
- "Build" still means run the full pipeline above. "Push" still triggers the commit-and-push flow. Note that you also build automatically after finishing any change (see **"Always build after changes"** under Build & deploy pipeline) — an explicit "Build" is just a way to force it again.
- The skill's historical "deliver patch + zip + in-flight bullet → swap to hash" rituals are claude.ai artefacts; just commit directly with a good message body.
- When a new piece of knowledge surfaces (a new chokepoint, a non-obvious file naming convention, a regression cause), update either this CLAUDE.md or the `appmanager-fork` skill so it persists into the next session.

## Commit / branch process

- `custom` is a growing stack of small, self-describing commits on top of upstream `master`. **Keep appending commits**; when a new upstream version is released, **rebase `custom` onto it**. There is no goal to squash the history down to a fixed number of commits — do not autosquash/collapse the stack.
