# Backup, restore and batch operations

The batch progress page and operation log, backup parts, per-app options, cancel, staged replacement, the install-source override, the `Android/data` mount and the backup dialog.

> Moved verbatim out of `CLAUDE.md` (2026-11-15) to keep that file under the size limit. `CLAUDE.md` holds the index; add new knowledge about this area **here**, not there.

| Concern | Notes |

| Batch-op progress **page** + pause/cancel | Full screen, not a dialog (白い熊, +116 — `main/BatchProgressDialog.java` and its two layouts are **deleted**). Two singletons behind it, and the split is the point: `batchops/BatchOpsProgressMonitor.java` answers *what is happening now* (a handful of in-flight items, replaced as they move on — right for a bar, and it throws away exactly the history a log is read for), while `batchops/OpLog.java` keeps *what has happened* — every app, stage and file, capped at 20 000 lines and trimmed in blocks of 2 000. The service calls `begin`/`finish` on both, the worker loop calls `publishProgress` and the per-item checkpoint, and the page observes both. The single chokepoint is still `BatchOpsManager.updateProgress(...)` (first call in every op loop) — it blocks while paused and throws `OperationCancelledException` on cancel, caught in `performOp(info, handler)`. **LANDMINE — backup and restore run one thread per core, so events from up to eight apps arrive shuffled.** A plain indented tree would then file one app's files under whichever app printed last, so `OpLog.ensureContext` re-announces the owning app (`Entry.continued`, drawn faded with `↳`) whenever the emitter changes: every line belongs to the app named directly above it, and nothing is inferred from position. Publication is a revision counter, not a copied list — `postValue` keeps only the newest pending value, so a burst from eight threads collapses into one redraw. **The log outlives the page**: folding the Mate XT destroys and rebuilds the activity, which is a normal thing to do during a long backup. Depth ladder = batch 0 · app 1 · stage 2 · item 3, rendered by `OpLogFormat` — the one renderer, shared with `OpLog.asText()` for Copy/Save, or the saved log would stop matching the read one. **A failure's reason gets a line of its own** (白い熊, +157): appended to the summary it became the tail of `白い熊 自由作業盤 · 2.1 s · 14.1 MB · Row too big to fit into CursorWindow…`, and since rows are middle-ellipsized what survived on screen was `14.1…to CursorWindow` — the size and the end of a sentence, with the part that names the failure elided. `OpLog.appFinished` now emits the summary and then the reason one level deeper, so it starts at column 0; both surfaces follow, because the renderer is shared with `asText()`. Rows are monospaced, single-line, ellipsized in the **middle** (a wrapped line restarts at column 0 and reads as a new entry; a proportional face breaks the ladder), and a tap shows the whole line. Depth comes from `BackupProgressListener.onItem` (a `default` no-op added beside `onStage`/`onDestination`/`onBytesWritten`), fed by `BackupOp.reportBytes`/`RestoreOp.reportFiles` naming every archive member with its real on-disk size, plus counts for extras and rules and the sister app's own app-data progress. `BatchOpsManager.itemListener` feeds monitor **and** log, remembering the last stage so a leaf does not blank the header. Opened from two places, because one is not enough: `MainActivity`'s `ACTION_BATCH_OPS_STARTED` receiver only exists while the app list is resumed, so `BatchOpsService` also launches it (needs `FLAG_ACTIVITY_NEW_TASK`; a refusal under background-launch rules is a silent no-op and the notification still opens it). **Rule (白い熊): always for backup/restore/backup-APK/delete-backup/import-backups, otherwise only when more than one app is involved** — `BatchOpsProgressActivity.shouldAutoOpen`. Gated by the `batch_progress_dialog` pref, whose key is unchanged so old exports still carry it. Colours are `ColorPrefs.OPLOG_*` and the size/timestamp toggle `fonts/OpLogPrefs.java` (own prefs file, classified APPEARANCE), settable in the *Batch operation log* group on the 白い熊 応用管理 UI page. |
| **Backup parts have colours, and every surface uses them** (白い熊, +121…+133) | `backup/dialog/BackupParts.java` is the legend — one colour and one glyph per part (APK ice blue, internal data theme yellow, external amber, app-supplied green, OBB/media violet, cache grey, extras rose, rules orange) — and `BackupPartRows.java` draws it everywhere a part is chosen: the single-app options list (`partRow`), the batch table (`partPill`), the category pills (`plainPill`), the restore chooser (`showRestoreOptions`). The palette is **fixed, not settable**: it is a legend, and a per-screen colour picker would make it worth nothing. `BatchBackupTableDialog` is the batch backup surface — one row per app with its own parts and a foldable app-supplied section — because one set of flags for five hundred apps is only right when they are all the same kind of thing. `RestorePartsTable` is its mirror, and it exists because batch restore used to build its choice from `getWorstBackupFlag()`, the **intersection** of every selected backup: a part only some archives carried could not be chosen at all, and the apps that had it silently did not get it back. Each app also picks **which** backup to restore from, since the parts are a fact about that archive. |
| **Per-app options travel with the operation** (白い熊, +121/+131/+133/+136) | `BatchBackupOptions` carries three per-package maps beside the batch-wide values — `mPerPackageFlags`, `mPerPackageRelativeDirs`, `mPerPackageAppData` — each in the parcel (parallel arrays, never a Serializable Map) and the JSON. `getBackupOpOptions`/`getRestoreOpOptions`/`getDeleteOpOptions` prefer the per-package entry and fall back to the batch value. **LANDMINE — there were TWO places building these options.** `AppBackupDialogFragment` had its own copy of `startOperation` still calling the three-argument constructor, so every per-app field added since was silently dropped on the path a single app takes: choosing every App-supplied category and pressing OK backed up whatever was stored instead, with identical logs either way. `OperationInfo.toBatchOptions()` is now the one builder and both dialogs call it. |
| **Choosing App-supplied categories: Save vs OK** (白い熊, +133) | `AppDataCategoryPicker` answers two different questions and used to answer only one — every close wrote the app's stored preference, so narrowing one backup narrowed every future one. **Save** stores and applies; **OK** applies to this backup only; **Use app's defaults** forgets the stored choice; Cancel does nothing. A run-scoped choice rides `BatchBackupOptions.mPerPackageAppData` → `BackupOpOptions.appDataCategories` → `AppDataTransfer.export(..., requested, ...)`, where **null means "use what is stored" and an EMPTY array means "none of it"** — the parcel round trip preserves the difference. Requested ids are re-checked against what the app offers right now, because an app updated in between could refuse the whole export with "unknown category". `BatchBackupTableDialog` never writes the preference at all: the table is a working surface you sweep across forty apps, and every tap used to land in `AppDataSelection`. |
| **The progress page says where you are** (白い熊, +140…+143) | `BackupOp`/`RestoreOp` build a **plan** of the stages the run will actually announce (APK only if the APK is going, KeyStore only if there is one, App-supplied only if the app really has a door) and each announcement looks itself up in it — planned, never counted, because the data step announces itself once per directory and a running counter would walk the total upward while you watch. The number is a `ForegroundColorSpan` in `ColorPrefs.OPLOG_BATCH`, carried on the same CharSequence that feeds the log line **and** the in-flight header. **It is repeated on every progress line**, not only the stage heading: a 6 GB export writes thousands of lines and the heading scrolls hours out of reach. **LANDMINE — `OpLogAdapter.append` used to blanket the appended range with the row colour**, which wins against any span already inside it (for one attribute the span added last draws), so the marker was applied at the source, copied faithfully, and silently repainted; the base colour is now laid into the gaps between existing colour spans. The three passes after the app hands its archive over — storing, encrypting, checksumming — are stages of their own with the size they are about to walk, and restore has the mirror three. A sister app whose byte counter goes **backwards** gets a line saying so: that is a second pass over the same data, and nothing else in the log marks the boundary. |
| **Cancel reaches inside one app** (白い熊, +143) | `BatchOpsManager.updateProgress` checks once per **app**, before that app's work — right for a batch, no use at all for a single app that takes twenty minutes, where Cancel had nothing left to reach and killing the process was the only way out. `BackupOp`/`RestoreOp` now check at every stage boundary (`checkCancelled`), the 6 GB staging copy checks every few megabytes (`copyCancellable` — `IoUtils.copy` is one call over gigabytes and sees nothing raised during it), and `AppDataClient.transfer` takes a `Cancellation` hook consulted by its wait loop, which polls every **1 s** rather than 5 and tells the sister app to stop before walking away. **Both ops rethrow `OperationCancelledException` ahead of their catch-all**, or a cancel is dressed up as "could not back up" and counted as a failure by the batch that asked for it to stop. |
| **Backups are replaced only after the replacement exists** (白い熊, +137) | `BackupItem` writes into a hidden `.name` staging directory beside the target; `commit()` renames it into place and **only then** deletes the previous backups. **LANDMINE — the constructor `mkdirs()`-es the real directory up front and cleanup used to delete only the staging one**, so every failed, cancelled or killed backup left an empty folder standing for ever. `cleanup()` now removes the real directory too, *only when it is empty*. `backup/BackupCleaner.java` + `BackupCleanupDialog` find the ones already on disk — empty folders, half-written `.name` directories, and directories with no readable metadata — reachable from Settings → Backup/restore and the ⋮ menu on 保存一覧. **A directory carrying readable metadata is never a finding**, whatever the database thinks, and an unreadable one counts as a backup rather than as rubbish. The overwrite warning now names what it will do and where "Back up multiple" lives; toggling that switch in the dialog is a decision about **this** backup and is deliberately not written back to the preference (+145). |
| **Per-app install-source override, set the session OWNER like `pm install -i`** (白い熊, +055, supersedes the global +052/+054, 2026-10-29) | A RASP-hardened app (`cz.csas.georgego`, Talsec freeRASP) refuses to run unless installed from a store (its "Security Check" Error 1007), which it reads off the install **session owner** — what `pm install -i <store>` and Aurora set. **The lever is the `PackageInstaller.createSession` OWNER arg** (3rd param): on this stock Huawei build it becomes BOTH the installing and the initiating package. The other mechanism, the `SessionParams.installerPackageName` field, is a different thing and is **refused for the shell uid on stock Huawei** (`canChangeInstaller` false, line ~908), so a restore that set only it recorded no installer at all. **Measured 2026-10-29:** `pm install -i com.android.vending <apk>` on a FRESH package → Success, no prompt, `installerPackageName=com.android.vending` — even though this phone's `com.android.vending` is **microG's FakeStore (no `INSTALL_PACKAGES`)**. So +052's "owner must hold `INSTALL_PACKAGES`" guard was wrong, and +054's "do it for every restore" was too broad (白い熊: most restores must keep looking like restores). **+055 is per-app opt-in.** `apk/installer/InstallSourcePrefs.java` (own prefs `shiroikuma_install_source.xml`, key=pkg → store package; travels in Settings export) is the source of truth. `PackageInstallerCompat.openSession` is reverted to the +160 default (shell owner `null`) **except** when `InstallSourcePrefs.getInstallSource(mPackageName)` is set, is not our own package, and the store is installed → that store is the session owner. The toggle lives in **`AppBackupDialogFragment`** (Default / Play Store / Huawei App Gallery / Custom); it is embedded in each new backup (`BackupMetadataV5.installerSourceOverride`, optional `installer_source_override`, read with `optString` so old backups restore unchanged) by `BackupOp`, and `RestoreOp` writes it back into `InstallSourcePrefs` before installing, so it reaches other phones and persists. **`dumpsys` on this EMUI never prints the initiating field** — verify by behaviour (the app runs). **Only affects NEW installs** — set it for the package, then re-restore. `com.android.vending` here (Aurora/microG); some apps want `com.huawei.appmarket`. See [[restore-initiating-package-rasp]]. |
| **LANDMINE — `Android/data` is a REAL mount on the Mate XT, not the FUSE view** (白い熊, +044, measured 2026-09-17) | `RestoreOp.restoreDirectory` skips `chown`/`restorecon` for external data on the standing assumption that `/storage/emulated/0/Android/{data,obb,media}` is FUSE-emulated storage, where uid, gid and mode are **synthesised** from the path so nothing written there matters. On this phone that is **false for `Android/data`**: it is its own f2fs partition (`/dev/block/sdd88` on both `/mnt/user/0/emulated/0/Android/data` and `/storage/emulated/0/Android/data`), so extracted entries keep the **archive's own modes** — 0700 dirs / 0600 files, because such a tree was backed up from the app's *internal* data — under `shell:shell`. The app (`u0_aNNN`, group `ext_data_rw`) then cannot traverse its own external files dir: `File.listFiles()` answers **null** and the app crashes on launch, while the restore itself reported success. **`chown` is not the fix and the skip stays** — it is `EPERM` for the shell on that mount — and it is not needed: a file the shell creates there lands `shell:ext_data_rw 0660` and the app reads it happily. Only the preserved restrictive modes break it, so the restore ends with `chmod -R a+rwX` over the tree (capital `X`, so a directory becomes traversable and a data file is never made executable). **Best-effort, never a throw**: the top-level `<pkg>` directory is app-owned and refuses `chmod` with `EPERM` — expected, harmless (it is already traversable), and `chmod -R` walks on past it, so a non-zero exit is the normal case and is only logged. **Internal data is deliberately left alone**: the `chown` there hands the app real ownership, and `a+rwX` on `/data/data/<pkg>` would publish its private files to every app on the phone. |
| **The way back into a running or finished batch** (白い熊, +132/+142) | `@id/operation_bar`, pinned in the main `AppBarLayout` like the privilege alarm. Closing the progress page never stopped anything — the work is a foreground service — but the only route back was the notification, so the bar states what is running (or what finished) and opens the page. The progress page's bottom bar is **Pause · Leave running · Cancel**, Cancel alone in red, because with Cancel as the only visible way out that was something you had to risk a backup to find out. `BatchOpsProgressMonitor.noteResultSeen()` is set when the page draws a *finished* operation, and the bar hides on it: closing a log and finding a banner offering the log you just closed reads as a leftover. **LANDMINE — `setHostForeground` was a boolean and is now a counter**: moving from the list to the page runs the new screen's `onResume` before the old one's `onPause`, so the last write said "background" while a window of ours was plainly on top, and the un-themeable system banner flashed over the page announcing it. The completion notification is themed via `RemoteViews` (`notification_shiroikuma.xml`, a box painted the ink colour around one painted the background colour, since RemoteViews can set a colour but not build a bordered drawable) — **only the completion one**: a custom view replaces the template that draws the ongoing notification's progress bar. Since Android 12 the platform's own header strip above it cannot be repainted. |
| **One dialog holds every backup action** (白い熊, +72) | `backup/dialog/AppBackupDialogFragment.java` — what the long-press opens. It replaced a two-line chooser ("Backup", then "Restore or delete…" which opened the bottom sheet), where the one thing you came for — **the backups themselves** — was always a screen away and *Backup* was a list line pretending to be an action. Now: the app's backups as a **tick list** (base backup pre-ticked, same default as the sheet), `Restore` (exactly one ticked) / `Delete` (≥1) / `⋮` freeze-unfreeze as pills under it, and **`Back up` as the dialog's own positive button** beside Cancel. It **reuses `BackupRestoreDialogViewModel`** — same loader, same `prepareForOperation`, same `BatchOpsService` hand-off — so behaviour is identical to `BackupRestoreDialogFragment`, which stays for batch selections and app details. Four things it must keep doing: **(1)** the positive button is wired in `onStart()` via `getButton(BUTTON_POSITIVE).setOnClickListener` so a click does **not** dismiss — the view model carrying the operation dies with the fragment, and dismissing before `startOperation` would drop the op on the floor; `ForkDialog.bordered` (not `present`) is the right helper for exactly that reason. **(2)** everything is inflated from `builder.getContext()`, the yellow-on-black **overlay** context — the fragment's own context has the activity theme, and rows inflated from it lose the tick mark (the M3 multi-choice item declares it as `app:drawableStartCompat`, which only the AppCompat inflater factory honours). **(3)** row labels are formatted on a **background thread**: `BackupMetadataV5.toLocalizedString` is `@WorkerThread` because it walks the backup directory to size it. **(4)** `processPackages` runs only when `savedInstanceState == null`; the LiveData is sticky, so a rotation re-renders from what is already loaded. `Back up` honours "Skip backup method dialog" the same way the sheet's backup-only path does, and warns before overwriting only when a **base** backup exists (`BackupInfo.hasBaseBackup()`, more precise than the sheet's app-count arithmetic). |
