# Main list — rows, pills, panes, lenses, layout, top bar

Selection toolbar registries, row pills and notes, the shelf, lenses, sort, the app pane and batch pane, per-geometry layout, separators, the icon cache and the top bar.

> Moved verbatim out of `CLAUDE.md` (2026-11-15) to keep that file under the size limit. `CLAUDE.md` holds the index; add new knowledge about this area **here**, not there.

| Customisable selection toolbar registry | `app/src/main/java/io/github/muntashirakon/AppManager/main/MainToolbarPrefs.java` — add new actions to `ALL_KEYS` + `idForKey`/`titleForKey`/`iconForKey`. An item in the menu XML alone is **invisible**, because the toolbar is rebuilt programmatically. |
| **Retiring a registry key moves the pill unless you say otherwise** (白い熊, +038) | `MainToolbarPrefs.alias(key)`. Both pill registries drop a stored key they do not recognise and then append anything missing from both lists to the **end** of the visible order — so renaming a key is not a rename: the pill silently jumps to the back of the pane. `alias` maps the retired name to its replacement while the stored order is parsed, which keeps the position and means the old name never has to be recognised anywhere else. First user: `clear_data_cache` → `clear_data`, the batch bar's "Clear" pill (it opened a dialog asking data or cache; it is Clear data outright now, and batch **clear cache** therefore lives only in One-click ops and the pane's own hidden `clear_cache` pill). **Sister landmine in `AppPanePrefs`**: adding a key to `DEFAULT_VISIBLE` is **inert** on any install whose pane has been edited — once both stored orders exist, reconciliation only promotes a key missing from *both*, and a key that was already in `ALL_KEYS` is sitting in the hidden list for ever. Hence `AppPanePrefs.migrateClearDataVisible`, a one-shot promotion called from `AppManager.onCreate` beside the freezing-method migrations, same shape and same reason. The pane's `clear_data`/`clear_cache` keys had existed since +118 with **no implementation** — they fell through to the default branch and opened App info — and now run the ordinary batch op over one package via `MainActivity.runSingleAppOp`, so a single app is a batch of one and gets the progress page and the operation log rather than a second implementation. |
| Batch-op completion snap (main list) | `MainViewModel.applyBatchOpResult(op, result, packages, failed)`, called from `MainActivity`'s `ACTION_BATCH_OPS_COMPLETED` receiver, snaps the list to its final state in **one** pass instead of letting the system's throttled per-package change broadcasts repaint it row-by-row over many seconds. For ops with a cheap in-memory state change it mutates the affected rows directly, then re-sorts + re-filters once: **freeze/unfreeze** → `ApplicationItem.setFrozenStateForBatchOp(frozen)` (keyed off `freezeTargetForOp`), via the shared `snapApplicationItems(targets, mutator)` helper; **reinstall** (`OP_INSTALL_EXISTING`) → `ApplicationItem.setInstalledStateForBatchOp()` (flips `isInstalled=true`, so rows drop out of the *Uninstalled apps* filter at once); **uninstall** (`OP_UNINSTALL`, `keepData=false`) → `snapUninstalledApplicationItems(...)`, which per-row mirrors `AppDb.updateApplicationInternal`: an **updated** system app stays installed (left untouched), a **pure** system app or any app **with a backup** flips to `isInstalled=false`, and a user app **with no backup** is removed outright. Any **other** op falls back to a targeted re-read (`updateInfoForPackages`). The optimistic in-memory branches only run when the op `ranToCompletion` (`result != RESULT_CANCELED`); on cancel the package list names every queued app but the unprocessed ones weren't changed, so it falls back to the true-state re-read. The trailing OS broadcasts then merely confirm the same state, so there's no visible row-by-row churn. When adding a new op whose result changes a filterable flag, give it an in-memory snap branch here rather than relying on the re-read/broadcast path. |
| Profile pills (per row) | `MainRecyclerAdapter.mPackageToProfileNames`, rebuilt by `loadProfileMembership()`. Trigger via `reloadProfileMembership()` on pull-to-refresh, on resume, and on the `AddToProfileDialogFragment.RESULT_KEY` fragment-result signal sent after a successful add. **Right-aligned since +94** (see the row-pill entry below): the strip lives in a `HorizontalScrollView` with `fillViewport="true"` over a `LinearLayoutCompat` at `gravity="end"` — that pair is the whole trick, stretching the strip to the viewport so `end` has something to push against, and scrolling sideways rather than wrapping when there are more pills than fit. The `+` is **outside** the scroller, so it can never be scrolled out of reach. They are no longer `Chip`s in a `ChipGroup`. |
| Per-app notes (main list + app details) | Free-text note attached to a package. Store: `utils/AppNotesManager.java` — a dedicated SharedPreferences file `shiroikuma_notes.xml` (key = package name, value = note; blank text **deletes** the key). Keyed by package only (multi-user packages share one note). The view/edit dialog is the shared static `AppNotesManager.showNoteDialog(ctx, pkg, label, onSaved)` (wraps `TextInputDialogBuilder`; multi-line, pre-filled, Save persists, blank deletes; optional `onSaved` runnable) — called by both `MainRecyclerAdapter.showNoteDialog` (onSaved = row refresh) and the app-details **Note** horizontal action button (`AppInfoFragment.getHorizontalActions`, an `ActionItem` before Uninstall; onSaved = null, the main list re-binds on resume). Because the store is its **own** `shared_prefs/*.xml`, **Settings export/import covers it automatically** with no change to `SettingsBackupManager`. On Save it refreshes just that row via `notifyItemChanged(holder.getBindingAdapterPosition())` (re-read at save time, **never** the stale bind position). Strings `note` / `note_blank_deletes_helper`. **UI: one pill in both states (白い熊, +94)** — `@id/note_pill`, right-aligned at the end of the label line, bound by `MainRecyclerAdapter.bindNotePill`. With a note it shows the note glyph plus the note's **first line**, ellipsized to what the row can spare (the full note is the `contentDescription`/tooltip); with none it is the same pill holding only `drawable/ic_note_add_24dp.xml`, pinned to `RowPills.ADD_WIDTH_DP` so it is exactly as wide as the tag `+` beneath it. It replaced a compound `drawableEnd` on the `label` (has-note) plus a `+` floating over the column's top-right (no-note): two controls for one affordance, in two places, neither able to show what the note *said*. **How wide it grows is settled at measure time, never at bind time** (白い熊, +95 — +94 guessed a fixed half of the line and left a gap between a short app name and the note): `main/LabelLineLayout.java` is the label line, and it exists for one rule — **the app name in full and not one pixel more; the note takes all the rest, reaching back to exactly where the name ends**. The name is `wrap_content` and **unweighted**, `@id/note_slot` (the `FrameLayout` around the pill, `layout_gravity="end"`) is the **only** weighted child, so it absorbs every remaining pixel. Weights alone cannot finish the job: weight on both splits the surplus (the +94 gap), weight on the slot alone leaves it **0 px** — the note gone from the row — whenever the name is longer than the whole line. ConstraintLayout answers this with `layout_constrainedWidth` against the pill's minimum and **`ConstraintLayout` is not a dependency here**, so `LabelLineLayout.onMeasure` caps the label at `available − (the other children + their margins + RowPills.ADD_WIDTH_DP)` before calling super — below the cap the name is untouched, above it the name ellipsizes (as it must anyway) and the note keeps its floor. Floor of the cap is **half the line**, or a 3–4-column grid would reserve away the whole name. `setMaxWidth` is called only when the value changes (it requests a layout). The **debug star sits before the pill**, since it is INVISIBLE rather than GONE for a non-debuggable app and would otherwise hold the pill ~24dp off the column's end, breaking the shared edge. The pill repeats the app icon's two guards (+82): a tap in **selection mode** extends the selection, and `setOnLongClickListener(v -> itemView.performLongClick())` hands the long-press back to the card (a clickable child swallows it, and this child is half a row wide). |
| **Row pills are built in one place** (白い熊, +94) | `main/RowPills.java` — the note pill, the tag pills and the two **add** affordances all come from this one builder, because the ask was that the add controls be *uniform*: same stadium outline, same pinned width, same faded ink, stacked into one column at the row's right edge. Two styling blocks agreeing with each other today is not uniformity; one builder is. Shape = the fork's pill language, shared with the Snooping status pills (transparent fill, hairline stadium — corner radius past half the height, which the framework clamps — plus a ripple of the same hue), built in code because the accent is the configurable theme's. **Alpha carries the hierarchy**: an add affordance is faded (0.55) — it is an invitation, not information; a written note is drawn below full strength too (0.45 outline / 0.80 ink) so it reads as a margin note rather than a second title; a tag pill alone is full-strength, being a fact about the app. `tagPill` returns **`LinearLayoutCompat.LayoutParams`**, not the `ViewGroup.MarginLayoutParams` it descends from — LinearLayout converts foreign params through `LayoutParams(ViewGroup.LayoutParams)`, which copies width and height and **silently drops the margins**. `battery/MainCardBinder` binds the same pills through the same builder (its note pill now works — it used to show a `+` with no listener behind it), so the battery header and the list cannot drift. |
| Profile file resolution | `ProfileManager.resolveExistingProfilePath(profileId)` returns the actual file by matching its stored id (scanning if the canonical name doesn't exist). Use this when writing back to a profile rather than `findProfilePathById`, which assumes the filename stem == id. |
| App-icon cache (main list) | `app/src/main/java/io/github/muntashirakon/AppManager/self/imagecache/ImageLoader.java` caches icons in two layers — in-memory `LruCache` + on-disk `images/<tag>.png` (`ImageFileCache`, 7-day-mtime GC, never a full wipe) — keyed by a **version-unaware tag**, so a reinstall keeps the **old** icon until the GC. The main list keys each row by `ImageLoader.versionedTag(packageName, lastUpdateTime)` → `"pkg@time"` so a reinstall busts both layers. **Set the same versioned tag on both `holder.icon.setTag(...)` and `displayImage(...)`** (`MainRecyclerAdapter` ~line 464) — they must match or the recycled-view guard never binds the bitmap. Feed it a **live** `lastUpdateTime`: `MainViewModel.getNewApplicationItem` sources it from `getPackageInfo` (not the DB-cached `app.lastUpdateTime`, which lags reinstalls — the "some icons refresh, some don't" cause). Other icon surfaces (app-details, usage, running-apps, etc.) still use the bare `packageName` key. |
| **Pill shelf under the toolbar** (白い熊, +118) | `main/ShelfView.java` + `main/ShelfPrefs.java` (own prefs file `shiroikuma_shelf`, JSON, classified **TOOLBAR**). A pill is either a **saved view** — filter flags + sort + reverse + profile filters + search query, captured together because they only mean anything together — or a **screen**. `+` sits **outside** the scroller (the +94 trick: a `+` inside a scrolling strip is the one control you cannot reach once it overflows). The strip is a horizontal `RecyclerView` **because reordering has to be a drag**, and `ItemTouchHelper` does drags properly; the order is persisted on **drop**, not per move. Tapping the active pill **clears back to the plain list**, so one pill is both the way in and the way out. Applying goes through `MainViewModel.applyView(...)` — one pass that sets everything and runs the pipeline **once**; the individual setters would re-filter five times and re-sort twice per tap. Two of the ready-made presets (recently changed, biggest apps) exist here precisely because they do **not** deserve a screen: they are this list with a sort. |
| **Lenses — a "special page" is a state of the main list** (白い熊, +162…+167) | `main/lens/MainLens.java` + `MainLenses` (registry) + `BackupsLens` · `SnoopingLens` · `SisterAppsLens`. A lens changes **what some row elements show** and which apps are on the page; everything else — filters, search, profile filters, saved views, selection, the batch pane, the app pane, the frames, per-geometry columns, the separators — is the main list's own and untouched. The plain list is "no lens", and the way out is the way in: tapping the lit shelf pill again. **The ids are the SAME strings the shelf already stored** (`ShelfPrefs.SCREEN_BACKUPS`/`SNOOPING`/`SISTER`), so pills made before lenses existed keep working with no migration — never rename one. **What a lens deliberately cannot do**: take over the row's click (a tap unrolls the pane, +118, and keeping that was the point) or contribute filter flags (those are a persisted bitmask *and* the wire format of a saved view; a lens narrows through `includes()` instead). Rendering goes through **`MainCardBinder.renderCustomRightLines`**, extracted so the lens and the remaining tracker screen cannot drift. **LANDMINE — `prepare()` runs BEFORE the include filter**, over every candidate: for two of the three lenses membership *is* what preparation works out (盗み見 needs a `SnoopingResolver` pass, 仲間 needs `GET_META_DATA`), neither of which an `ApplicationItem` carries. **Caching is not optional**: a keystroke re-runs the whole pipeline, so an uncached 盗み見 would re-resolve every app per character — verdicts are cached per package against `lastUpdateTime` (an update is what changes what an app can do, and moving that timestamp is how an update announces itself), and both lenses check `ThreadUtils.isInterrupted()` so a keystroke mid-pass cancels and resumes from the cache. Pull-to-refresh calls `MainViewModel.invalidateLensCaches()`, which is the only thing that clears them. The single chokepoint is `MainViewModel.publish(...)` — every `postValue` in the filter path goes through it. `ShelfView.setActiveId` is view state while the lens is view-model state, so `MainActivity.relightLensPill()` reconciles them after every shelf reload (folding the Mate XT rebuilds the activity). **Battery and Process stay real screens** — their rows are per-uid and per-pid, not `ApplicationItem`s. |
| **Sort is its own control, not part of the filter sheet** (白い熊, +163…+165) | `main/SortMenuPopup.java`, opened by `action_sort` on the top bar right of clear-filters. A filter is set once and left; a sort is flicked between while looking at the same list, so it costs a tap rather than an open-scroll-dismiss. `MainListOptions.getSortIdLocaleMap()` returns **null** (which `ListOptions` already treats as "hide the sort section"), and the orders themselves live in the new static `MainListOptions.sortIdLocaleMap()`; every other `ListOptions` subclass keeps its in-sheet sort. The active lens's own orders are appended to the same panel under a heading, but keep a **separate id space and a separate view-model field** — the list's sort ids are the wire format a saved view stores, while a lens index means something different in every lens. **A framework `PopupMenu` cannot be used**: its row height, padding and lack of separators are baked into the platform's layout, so the panel is drawn by hand — rows packed to the text, a hairline between them, a wash plus a filled marker on the selection, and the kxkb text-width underline for the group heading. It hugs its content and otherwise runs to the bottom edge, measured from the anchor rather than assumed (the Mate XT's window height differs folded, unfolded and in multi-window). Paired fix: `MainViewModel.setReverseSort` used to submit its re-sort *before* assigning the new value and read the field rather than a local — a race that only showed once Reverse became a one-tap toggle. |

| **A tap unrolls a pane; it does not leave** (白い熊, +118) | `main/AppPaneBinder.java` fills `@id/app_pane`, a `GONE` container at the bottom of `item_main.xml`, which is now a **column** (row, then pane). **LANDMINE — the pane is part of the row and NOT an inserted adapter item**: every selection call in `MultiSelectionView.Adapter` is keyed by **adapter position** (`select`/`deselect`/`isSelected`/`selectRange`), so an inserted item would shift every position after it and quietly corrupt the selection. | **One layout per geometry** (白い熊, +88) | A column count that suits the folded cover panel is wrong unfolded and wrong again rotated, so all three list screens (main list, process monitor `MonitorPrefs`, battery history `BatteryLayoutPrefs`) store **one pick per geometry** rather than one pick. `utils/LayoutGeometry.java` is the single place that decides what a geometry *is*: orientation + `Configuration.smallestScreenWidthDp` → keys like `p403` / `l819`, and the pref key is `columns_<that>`. **`smallestScreenWidthDp` is the fold fingerprint** — the smaller side of the window in dp, so it moves when panels unfold (Mate XT ≈ 403 folded, ≈ 819 unfolded) and stands still when the same geometry is merely rotated, which the orientation letter covers. No window-manager dependency and no OEM fold API: a device with three panels or none gets sensible keys for free, and multi-window falls out of the same rule because the configuration has described the *window* rather than the display since API 24. **LANDMINE — pass an activity or view context, never the application context**, or every multi-window geometry collapses onto the full-screen key (`MainRecyclerAdapter` feeds it `cardView.getContext()`; the prefs *file* still opens on the application context, which is unrelated). **Migration:** the pre-geometry bare `columns` key is still read as the seed for any geometry never set, so an existing choice carries into all of them once; writes only ever touch the per-geometry key. Re-applied on geometry change by the activity being recreated (none of the three declares `configChanges`), plus an `applyListLayoutIfGeometryChanged()` guard in each `onResume` — and for the main list inside `refreshForkAppearanceIfChanged()`, so the multi-window side-by-side path (`onTopResumedActivityChanged`) is covered too. |
| **The right column is sized for ONE column; a grid must take the weighted path** (白い熊, +068) | `MainRecyclerAdapter.applyColumnProportions(context, holder, wideRight)` lays the row's three columns out two ways. `wideRight=true` is pure weights — centre `0dp` weight **1.35**, right `0dp` weight **1** — and cannot collapse. `wideRight=false` pins the right column to a **fixed pixel width** (`MainLayoutPrefs.rightColumnWidthPx`, measured from `RIGHT_COLUMN_REFERENCE` with the version line's own paint) and makes the centre column the sole weighted child, so a `LinearLayout` hands the centre only the slack the fixed sibling leaves. **That fixed width is sized for a one-column full-width row** and overruns a narrow grid card: there the centre column (app name, uid, package, date) is starved to zero — the app name vanishes and the uid/date truncate to `10…`/`11/…`, while the note/tag pills crowd the icon. It got far worse at +173, which widened `RIGHT_COLUMN_REFERENCE` from the 13-char signature `SHA384withRSA` to a full **36-char fork version name**, nearly tripling the pinned width; the `RIGHT_COLUMN_MAX_SHARE` (2/3) clamp does not save it, because `availableRowWidthPx` overestimates the real card (it subtracts only the icon, never the card padding, inter-column gap or margins). **Fix:** `onBindViewHolder` takes the weighted path whenever the grid is multi-column — `wideRight = (lens != null && lens.wideRight()) || mActivity.getListSpanCount() > 1`. `MainActivity.getListSpanCount()` reads the **live** `GridLayoutManager` span count (what is actually drawn — a fixed pick, or `AutoFitGridLayoutManager`'s measured count), never the preference, so it can never disagree with the screen. The fixed-pixel block survives only for the genuine one-column list, its designed home; on a grid the long version string shrinks or middle-ellipsises via `fitVersionPair` (`version`/`backup_version` are `ellipsize="middle"`, so they never hard-overflow). **Rule for a rebase: keep the span-count guard.** The display lenses' `wideRight()` alone does NOT cover it — the plain multi-column grid has no lens, and the filter-only lens 仲間 is stored in `mFilterLensIds` so `MainViewModel.getLens()` returns null for it; both reach `applyColumnProportions` with `wideRight=false` and would collapse again. |

| **The main top bar scrolls sideways** (白い熊, +84) | Every action on `activity_main_actions.xml` is `showAsAction="always"` (deliberately — `ifRoom` silently drops things into the overflow), and the **search field is the toolbar's custom view** at `MATCH_PARENT` (`MainActivity.onAuthenticated`, `ActionBar.setCustomView`). Fix: the `MaterialToolbar` now lives inside a **`HorizontalScrollView`** (`@id/toolbar_scroller`) in `activity_main.xml`. **The mechanism is the measure mode.** `HorizontalScrollView.measureChild` **ignores `lp.width` and always passes `UNSPECIFIED`**, so the toolbar is measured at its *natural* width: nothing is squeezed, and `ActionMenuView.onMeasure` sets `mFormatItems = (mode == EXACTLY)` → false → it falls back to the plain `LinearLayoutCompat` row instead of its cell-fitting pass. `fillViewport="true"` preserves the old behaviour whenever the bar *does* fit: the child is re-measured **`EXACTLY`** at the viewport width and the `MATCH_PARENT` custom view stretches as before. **LANDMINE — `MATCH_PARENT` means nothing under `UNSPECIFIED`:** `getChildMeasureSpec` turns it into `UNSPECIFIED`, and `androidx.appcompat.widget.SearchView.onMeasure` then falls back to `abc_search_view_preferred_width` (**320dp**), which on a ~430dp panel pushes every icon off-screen — i.e. the same bug, mirrored. Hence `AdvancedSearchView.setUnconstrainedWidth(px)` (fork-only; 0 = upstream behaviour), fed `R.dimen.main_search_bar_scroll_width` (240dp) from `MainActivity`. Do **not** use `SearchView.setMaxWidth` for this — it also caps the `EXACTLY` case and would stop the field stretching on the unfolded screen. Free consequences: `HorizontalScrollView` auto-scrolls to a focused child, so `focusSearch()`/the market-URI path still bring the field into view; `attachOverflowLongPress` still works, since it walks the toolbar's own children.
