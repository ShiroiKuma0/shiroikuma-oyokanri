# Privileges, start-up and threading

The privileged session (Shizuku/ADB), the splash trampoline, mode validation, component names, feature flags, main-thread privileged reads, reopening the last screen, `AppDb.sLock`.

> Moved verbatim out of `CLAUDE.md` (2026-11-15) to keep that file under the size limit. `CLAUDE.md` holds the index; add new knowledge about this area **here**, not there.

|---|---|
| Launcher resumes where you were | `main/SplashActivity.java` is a **trampoline**: it starts `MainActivity` and finishes, so the task it leaves is rooted at `MainActivity` and no longer contains it. Tapping the launcher icon while that task exists drops a **fresh** Splash on top, which used to stack a **fresh** `MainActivity` over whatever screen (and tab) the user was on — the task was never damaged, just buried. `onCreate` now computes `mLaunchedOntoExistingTask` = `!isTaskRoot() && ACTION_MAIN && CATEGORY_LAUNCHER` **first thing** (`getIntent()`/`isTaskRoot()` are valid from `attach()`, i.e. before `super.onCreate()`); if that and `Ops.isAuthenticated()`, it calls `super.onCreate` → `finish()` → `overridePendingTransition(0, 0)` and returns **before** the theme, `installSplashScreen` and `setContentView`, so nothing of ours is drawn and there is no flash. Both hand-off sites go through `handOff()`, which finishes instead of starting `MainActivity` in that case — including after the auth/ADB flow, which is the path taken when EMUI killed the process and the task was restored around us (privileges are up before the restored screen resumes). **`super.onCreate()` must still be called or the framework throws `SuperNotCalledException`.** |
| **A lost privileged session is reclaimed, and shown** (白い熊, +97) | `settings/PrivilegeWatchdog.java`. Every privileged call runs through the `IAMService` binder, and a Shizuku server restart (an update of 白い熊 雫, a stopped server, a killed user-service process) takes it with it. The **entire** reaction used to be `ServiceConnectionWrapper.onServiceDisconnected` nulling its field: `LocalServices.alive()` then answered false, `Runner.getInstance()` quietly returned the **no-root** shell and `ProxyBinder` fell back to local binders — nothing threw, nothing was shown, and privileged operations silently did nothing. `Ops.init` is reached only from `SecurityAndOpsViewModel` (the splash gate) and `MainPreferencesViewModel` (the mode picker), so the only cure was restarting the app. **Reclaiming is free when it is possible at all**: authorisation lives in the *server's* own persisted list and survives the restart, and the returning server **pushes a fresh binder** into our `ShizukuProvider` → `Shizuku.onBinderReceived`. Both that and the death notice already existed and were simply never listened for — no `OnBinderDeadListener` anywhere, and the one `OnBinderReceivedListener` was the transient sticky one inside `ShizukuOps.awaitBinder`, removed in its own `finally`. The watchdog is the listener that stays, installed once from `AppManager.onCreate` (the server pushes whenever it likes, including while no activity exists). **The reclaim is `Ops.init(context, false)`, never a bind of our own** — that method is the one place that knows how each mode is entered, corrects the session flags from the uid the service actually came up as, and re-runs `SelfPermissions.init()`. **LANDMINE — a deliberate teardown is indistinguishable from a death.** A mode switch tears the old service down before binding the new one and fires the same `onServiceDisconnected`; every such teardown in the app happens inside `Ops.init` (`LocalServices.stopServices` has no other caller, `unbindServices` is only reached from `bindServices`), so `Ops.init` brackets itself with `noteInitStarted()`/`noteInitFinished()` and a drop seen inside the brackets is ours. No timer separates the two. **Nothing is alarming until something is actually lost**: `sHadPrivileges` latches the first time the services are seen alive, so an install that has always been no-root never sees a red bar. `MODE_AUTO` counts as "Shizuku is the chosen route" — auto-detection hunts Shizuku first and the fork deliberately leaves the preference on auto whenever a manager is installed. Automatic reclaims gate on `ShizukuOps.isReady()` so `Ops.init` finds authorisation already in place and **raises no prompt**; only a tap on the alarm passes `interactive=true`. UI = `@id/privilege_alarm`, a pinned red bar inside the `AppBarLayout` below the progress indicator (no scroll flags, so it cannot be scrolled away), wired in `MainActivity.setupPrivilegeAlarm` and refreshed from `onResume` for whatever happened while we were away. Colours are the Snooping page's "allowed" pair (`0xFF6E0B14` on `0xFFFFD9DC`), **not** the theme yellow, which here would read as ordinary furniture; the icon pulses only in `STATE_LOST` and the animator is cancelled in `onDestroy` (an INFINITE animator holds its target view). Add `PrivilegeWatchdog.onServiceLost()` to any new way the binder can drop. |
| **LANDMINE — `Ops.isValidMode` must list every `@Mode`, `MODE_SHIZUKU` included** (白い熊, +045) | Upstream added the validator in 4.1.1 (`19c9f39a6` *Validate mode of operations*, 2026-08-24) and wrote out **five** of the six values in the `@StringDef` directly above it. Upstream never persists `shizuku`, so the omission costs upstream nothing; here it is the mode auto-detection is **meant** to land in, and the 4.1.1 sync therefore took the fork's privileges away on **every** start. Two halves broke at once: `setMode(MODE_SHIZUKU)` **threw** `IllegalArgumentException: Unknown mode of operation: shizuku` out of `autoDetectRootSystemOrAdbAndPersist` — *after* the Shizuku services had already come up — so `SecurityAndOpsViewModel`'s catch-all called `fallbackToNoRoot` and reported `STATUS_FAILURE`; and `getMode()` silently rewrote a stored `shizuku` back to `auto`, which is what made `case MODE_SHIZUKU` in `initLocked` dead code and the Settings mode-picker's own Shizuku entry throw. **The visible symptom was not "no privileges" but a frozen window**: each start tore the live session down, `PrivilegeWatchdog` reclaimed it, and each reclaim parked `LocalServices.bindAmService` for ~45 s **holding the `ServiceConnectionWrapper` monitor** — so the first main-thread privileged read ANR'd the page, Back was never dispatched, and with the reopen-last-screen feature (+146) the app came up on that frozen page at every launch. **Rule for every rebase: a `@Mode` value the fork adds must be added to `isValidMode` in the same breath, and a conflict in that switch is never "take upstream".** |
| **LANDMINE — a relative manifest name expands against `namespace`, NEVER against `applicationId`** (白い熊, +043) | AGP resolves `<activity-alias android:name=".intercept.BrowserInterceptor">` using the **`namespace`** (`io.github.muntashirakon.AppManager`), not the `applicationId` (`shiroikuma.oyokanri`). Upstream those two strings are the same, so upstream code may build a component name out of `BuildConfig.APPLICATION_ID` and be right; **in this fork it is always wrong**, and wrong in the most expensive way — `PackageManagerService.setEnabledSetting` throws `IllegalArgumentException: Component class … does not exist` for any app targeting P or later, so the call site dies rather than no-opping. `ActivityInterceptor.ALIAS_BROWSER` was exactly this: `FeatureController.modifyState(FEAT_INTERCEPTOR, …)` disabled the target activity, then threw on the alias **before** the `AppPref.set(PREF_ENABLED_FEATURES_INT, …)` at the bottom of the method, so unticking *Interceptor* in Settings → Appearance → *Enable/disable features* could neither finish nor persist and the Interceptor kept answering every `ACTION_VIEW` http/https intent in the system chooser. Fixed by spelling the namespace out, as the two sibling constants `AppDetailsActivity.ALIAS_APP_INFO` and `CodeEditorActivity.ALIAS_EDITOR` always did. **Rule: a `ComponentName` for one of OUR components is `new ComponentName(BuildConfig.APPLICATION_ID, "io.github.muntashirakon.AppManager.…")` — package from the applicationId, class from the namespace.** `BuildConfig.APPLICATION_ID` remains correct for intent-extra keys and authorities, which is most of its uses. |
| **A feature flag travels; its component's enabled state does not** (白い熊, +043) | `FeatureController` holds each feature in two places: the bit in `PREF_ENABLED_FEATURES_INT`, which lives in `shared_prefs/` and therefore rides in every settings export, and the component's enabled state, which lives in `system_server` and rides in nothing. `isEnabled()` **ANDs the two**, so when they disagree the feature disappears from our own UI (Labs, our open-with sheet) while the manifest entry keeps answering the **system**. They disagree on exactly the case this family is built for — a settings import onto a clean phone — and the `shiroikuma.appmanager` → `shiroikuma.oyokanri` rename did it to every install at once, since a renamed applicationId is a fresh install whose component states all start at *enabled*. `FeatureController.reassertDisabledComponents()` (called from `AppManager.onCreate` on a background thread — these are binder calls) re-asserts the **disables** the flags already record. **One-directional on purpose**: a flag that says *enabled* never re-enables a component, because a component disabled by some other route was disabled deliberately. Each feature is guarded separately so a name that does not resolve can never take the process down — which is precisely what the alias above did. `componentFor(key)` is the single mapping, shared with `isEnabled`. |
| **LANDMINE — a privileged read on the main thread hangs the whole app after every install** (白い熊, +033) | `AppDetailsSnoopingFragment.onViewCreated` called `SnoopingEnforcer.canEnforce()` inline, from the original 盗み見 commit. That reaches `SelfPermissions.canModifyAppOpMode` → `Users.getSelfOrRemoteUid()` → **`LocalServices.getAmService()`, which is `synchronized`** on the service-connection wrapper. It returns in microseconds while the `:am` server is bound and **blocks for the whole bind** while it is not — and the bind holds that same monitor from another thread (`PrivilegeWatchdog.reclaim` → `Ops.init` → `LocalServices.bindServices` → `ServiceConnectionWrapper.startDaemon`, parked on a `CountDownLatch` for the daemon). **The two meet on every fresh install**: replacing the package kills the old privileged server, the watchdog reclaims it, and the reopen-last-screen feature (+146) opens this very page while that is in flight. Symptom is a **black window and then the app dies** — which reads as a crash and is an **ANR**: `Input dispatching timed out … Waited 10006ms for FocusEvent`. **Diagnosis method, because the obvious ones fail**: `logcat -b crash` shows nothing (an ANR is not an exception), `/data/anr/*` is `system:system 0600` so the shell cannot read it, and `debuggerd -j` answers `root is required`. **`adb bugreport` is the way in** — it carries *VM TRACES AT LAST ANR* (the stored file) and *VM TRACES JUST NOW* (every process, dumped live), which is how the blocked frame and the lock **holder** were both identified. Fixed by asking on a worker and filling the banner in when the answer arrives; the page is useful meanwhile because every capability row does its own privilege check. Those two upstream tabs were answered the same way in **+034** — `AppDetailsComponentsFragment.onCreateMenu` (which also **caches** the answer and re-inflates through `invalidateOptionsMenu()`, since a menu callback cannot be deferred) and `AppDetailsOverlaysFragment.onCreate`/`onViewCreated`. **The one that finally bit was App info's (白い熊, +045)**: `AppInfoFragment.onPrepareMenu` read `MANAGE_SENSORS`, `Users.getUsersIds()` and `isSystemOrRootOrShell()` inline — and App info is built at **every** open of this page, because `setOffscreenPageLimit(4)` creates the first five tabs whichever one you land on. ANR trace of 2026-09-26 20:15:50: main thread in `onPrepareMenu → checkSelfOrRemotePermission → getAmService`, *"waiting to lock … held by thread 23"*, against `pool-3-thread-2` sitting in `PrivilegeWatchdog.reclaim → Ops.init → LocalServices.bindAmService` **parked 45 s** on the daemon latch (see the `isValidMode` row for why that bind was happening at all). Those three reads now run on the worker that method already had, their menu items **hidden until it answers**. **Still live and untouched**: `AppDetailsPermissionsFragment.getNotFoundString`/`getHelpString` (`GET_APP_OPS_STATS`, `canModifyAppOpMode`, `canModifyPermissions`), reached on the main thread while the App-ops/permissions lists render. **Rule: no `SelfPermissions`/`Users`/`LocalServices` call belongs in a lifecycle or menu callback.** |
| **Reopening the screen you were on** (白い熊, +146) | `main/LastScreenPrefs.java`. The +97 splash trampoline handles the easy half — while the task still exists `SplashActivity` finishes and the screen underneath resumes — but it can only resume a task that is **still there**, and EMUI drops ours while Android resets a task to its root when it is returned to after long enough away. Then the launcher builds a fresh task, `MainActivity` is created for real, and nothing in the task stack remembers 保存一覧 or an app's 盗み見 page. So it is written down: one `ActivityLifecycleCallbacks` installed from `AppManager.onCreate` records the resumed activity's own `Intent` (`toUri(URI_INTENT_SCHEME)`), and `MainActivity.reopenLastScreen` replays it — only from a genuinely fresh start (`savedInstanceState == null`, no data URI, so the `market://search` path is never hijacked) and **at most once per process**, so backing out of the restored screen leaves you on the list rather than in a loop. Returning to the main list clears the memory by itself, because `MainActivity` is recorded like everything else and recording it means "nothing to reopen". **An allowlist, deliberately** (`REOPENABLE`, class objects so a rename cannot silently disable it): this app is full of activities that must never be replayed — installer, keystore prompt, freeze-unfreeze trampoline, the progress page of a finished operation — and an intent carrying a `content://` URI would be replayed without the grant that made it work, so an intent with data is never recorded. Paired with `android:alwaysRetainTaskState="true"` on **`MainActivity`**, which is the task root because Splash is a trampoline. **LANDMINE — it must NOT be latched to once per process (+147, measured on the phone).** +146 set a static `sConsumed` on the first `MainActivity` of a process, which looked harmless and killed the feature: on EMUI a launcher tap can create a **second** `MainActivity` while the process is still alive (`dumpsys activity activities` shows it as repeating `[Main, screen, Main, screen]` pairs in one task), and every launch after the first found the latch thrown and went to the app list — exactly the bug the feature was meant to fix. Reading the record now **clears** it instead, and nothing is lost because the restored screen records itself again as it resumes. What replaces the latch as the "is this a launch?" test is **`MainActivity.EXTRA_FROM_SPLASH`**, set only by `SplashActivity.handOff()`: every other route to this window is somebody already inside the app asking for the list — `AppDetailsActivity`'s *back to main page* most of all — and reopening the screen they just left would fight them. Verified on-device: same pid, task cleared, fresh `MainActivity`, and the 盗み見 page came back. **The list underneath is not loaded while it is covered (+149)**: reopening creates this window and immediately buries it, so reading, sizing and sorting every installed app for a screen nobody is looking at merely starves the screen that IS on top of the same threads and the same privileged server. `MainViewModel.setLoadDeferred(true)` is set **before anything observes the item list** (observing is what starts the load, so the decision has to be made at the top of `onAuthenticated`, which is why the reopen intent is computed there and started at the end), and `MainActivity.kickDeferredListLoad()` runs it from `onTopResumedActivityChanged(true)` — the moment the list stops being invisible, whether because the reopened screen was closed or because there never was one. `mReopenInFlight` covers the gap where this window is briefly top-resumed before the reopened screen arrives, `onStop` clears it, and a 3 s fallback (guarded on the lifecycle actually being RESUMED, or it would fire the load underneath the very screen it was avoiding) covers a launch that never happens. Switch on the 白い熊 応用管理 UI page (*Screens*, default on); the prefs file is in `EXCLUDED_PREFS` — a remembered screen for an app another phone does not have is worse than no memory at all. |
| **LANDMINE — `AppDb.sLock` is one coarse lock, and the first-load scan holds it for minutes** (白い熊, +053) | `db/utils/AppDb.java`. Pressing **Restore** right after app start took **minutes** to populate, for every app — not George-specific, and nothing to do with backup size. On first load the main list runs `loadInstalledOrBackedUpApplications` → `getBackups(true)` (a full walk of the whole backup directory) + **`updateApplications(context)`, which held `synchronized (sLock)` for its ENTIRE run** — including a `PackageManagerCompat.getInstalledPackages(...)` with `GET_ACTIVITIES\|GET_RECEIVERS\|GET_PROVIDERS\|GET_SERVICES\|GET_SIGNING_CERTIFICATES\|MATCH_UNINSTALLED` for every package across users, through the privileged binder (minutes on a phone with many apps). The restore dialog's `processPackagesInternal` reads `getAllApplications(pkg,user)` + `getAllBackups(pkg)`, **both `synchronized (sLock)`**, so it **blocked behind the first-load rebuild** — the spinner was waiting, not working, which is why it was every app and only in the window right after launch. Two fixes (+053): **(1) root cause** — the heavy `getInstalledPackages` is gathered **outside** `sLock` (it reads no DB state) into a per-user map, and only the read-modify-write is held; a package changing in the gap is caught by the next broadcast-driven update, as before. **(2) insurance** — the read-only dialog uses new no-lock readers `AppDb.getAllApplicationsNoLock(pkg[,user])` beside the existing `getAllBackupsNoLock`; Room is thread-safe for a read concurrent with a write and the dialog re-reads on every op, so a few-seconds-stale row is harmless where a blocked dialog is not. **Rule: a read-only UI path must not take `sLock`; use the NoLock readers. A new heavy non-DB computation does not belong inside `sLock`.** See [[appdb-slock-first-load-contention]]. |
