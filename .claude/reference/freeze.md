# Freezing, gates, levels, suspension, uninstall

`FreezeUtils`, the four gates and their levels, hidden-package lookups, the always-protected apps, suspension and the uninstall chokepoint.

| Freeze chokepoint | `app/src/main/java/io/github/muntashirakon/AppManager/utils/FreezeUtils.java` |
| **A freeze is four gates, not one** (白い熊, +29) | `FREEZE_TOTAL` — force-stop → suspend → disable-user → **hide**, in that order, each best-effort, and the default freezing method. **Order is load-bearing**: hide last, because a hidden package is reported as *not installed* and the suspend/enabled-state calls then have nothing to act on. It is a **distinct method value** (`1 << 4`), not a mask of the others: the `FREEZE_*` constants are bit flags but every consumer compares them with `==`, and the value is the wire format of `FreezeRule` and of the per-app remembered method. Made the default by a second one-shot migration (`migrateDefaultFreezingMethodToTotal`, guard `PREF_FREEZE_TYPE_MIGRATED_TOTAL_BOOL`) firing only while the stored value is still exactly `FREEZE_ADV_SUSPEND` — same shape and same landmine as the +100 migration above it. **Measured 2026-09-10 on the phone (`HUAWEI GRL-LX9`, `SDK_INT 31`), confirmed by 白い熊 on the second phone; every claim below is a measurement, not a reading of AOSP.** **(1) The shell holds no `MANAGE_USERS`** — `pm hide` answers `SecurityException: Neither user 2000 nor current process has android.permission.MANAGE_USERS`, while `SUSPEND_APPS`, `CHANGE_COMPONENT_ENABLED_STATE`, `FORCE_STOP_PACKAGES` and `DELETE_PACKAGES` are all granted. So `PackageManagerCompat.hidePackage` **throws** here and the *Hide* freezing method had been silently degrading to *Disable* for as long as this fork has run on this phone. Hiding is reachable **only** through 雫's `DELEGATION_PACKAGE_ACCESS` (`DevicePolicyBridge.setHidden`), the same scope that carries `setPackagesSuspended` — so a phone whose Snooping suspend switch works can hide, and one without the delegation can do neither. **(2) `pm disable` (state 2) is refused outright**, and not only per component: at **package** level too — `SecurityException: Shell cannot change component state for <pkg>/null to 2`. Component level refuses **both** state 2 and state 3. The platform confines the shell to ENABLED/DEFAULT/DISABLED_USER on whole packages and to nothing at all on components (the +23 rule, now measured at package scope). **(3) Suspension is far stronger than its documentation** — it blocks the activity start (no process appears), the launcher path, and an **explicit broadcast to a resolvable receiver, even with `FLAG_INCLUDE_STOPPED_PACKAGES`**; and `pm suspend` on a *running* app kills the process by itself. **But it leaves `stopped=false`**, so the force-stop in Advanced suspend is **not** redundant: it is what sets the stopped flag. **(4) Disable-user is the resolution gate.** The cleanest discriminator is a content provider: suspended it answers `SecurityException: … not exported from UID …` (it resolved), disabled it answers `IllegalStateException: Could not find provider` (it does not exist). Suspension leaves every component resolvable; nothing else in the stack does. **(5) Two suspension slots.** The platform records suspension per *suspending package*: the shell path writes `suspendingPackage=com.android.shell`, the delegated path writes `android`. A shell `pm unsuspend` clears only the shell's slot and returns looking like success. `suspendBestEffort` therefore **prefers the admin slot** — it is the one `adb` cannot lift. **(6) A PERSISTENT system app keeps running through all four gates** (`com.huawei.hiview`: `flags=[ SYSTEM HAS_CODE PERSISTENT ]`, AMS `*PERS*`, process start time proving it was never killed — `ActivityManagerService.forceStopPackageLocked` deliberately spares persistent processes). The gates stop an app being *started*; they cannot evict a process AMS brought up at boot. **白い熊 自由作業盤 MIRRORS this gate set** (its `AppFreeze.freeze`/`thaw`, from its +086): it holds the same `DELEGATION_PACKAGE_ACCESS` and calls the same public SDK with a `null` admin, so it declined an automation contract from us and asked instead to be **told whenever the gate set changes** — a fifth gate, or hide dropped. Tell that repo before shipping such a change, or its thaw silently stops clearing everything ours applies. Its protected trio is the same three as `ProtectedAppsProfile.ALWAYS_PROTECTED`. |
| **LANDMINE — the FIRST render of the list comes from a different builder** (白い熊, +037) | `PackageUtils.getInstalledOrBackedUpApplicationsFromDb` builds the list the app opens with; `MainViewModel.getNewApplicationItem` rebuilds a row per package afterwards, off broadcasts and targeted re-reads. **Both must fill every live flag, or a new one is simply absent for the first ten seconds** and then appears — which reads as the app being slow to notice something it had in fact already read. The first builder set `isFrozen` from its bulk `getInstalledApplications` and stopped there, so a frozen row drew the *fallback* ice-blue snowflake with no rung colour, no shading and no badge: not level 2, **no level at all**, `isFrozen == true` with `freezeLevel == 0`. `isSuspendedApp` had the identical gap from +81 and was invisible only because suspension was rare. Both are filled there now, from the `ApplicationInfo` that builder already holds — free, and already carrying `MATCH_UNINSTALLED_PACKAGES \| MATCH_DISABLED_COMPONENTS`, which is what a hidden package needs to be seen at all. **Rule: any new per-row flag read from a live `ApplicationInfo` must be set in BOTH places**, and the fallback branches (no live info) must claim only what the DB actually knows — disabled, never a deeper rung. |
| **A freeze has a level, and the whole app says which** (白い熊, +034, badge reworked +035/+036) | `FreezeUtils.levelOf(ApplicationInfo)` = the **highest gate standing**, 0-4; `main/FreezeLevelBadge.java` turns that number into a colour and draws the badge; `ColorPrefs.FREEZE_LEVEL_1..4` + `FILM_LEVEL_2..4` are the ramp (defaults `theme_freeze_1..4` / `theme_film_freeze_2..4`, pale aqua → violet, all settable under *UI colors & fonts → Freeze levels*). Once each gate got its own switch, "frozen" stopped being one state and the row could no longer say which one you were looking at. Now: the main list's **film** is the rung's colour, the **snowflake** takes it too, and a **numbered ring sits BESIDE the snowflake at the same 26dp** (`@id/freeze_level_badge`, +036). It began overlapping the glyph's corner at 16dp, which cost the digit most of its size; beside it, it is simply legible. **It fits a 60dp icon column only because it can never share the line with the ✕**: that one is shown for a RUNNING app (`isInstalled && !isFrozen && !isStopped`), which is exactly freeze level 0, while the badge appears from level 1 up — check that invariant before adding anything else to that row. **The badge is a RING, never a disc** (白い熊, +035): hairline outline in the rung's colour, the digit in the same colour — the fork's own pill language, and the right way round for a mark drawn *on* the glyph, where a filled disc punched a solid coloured hole that read as damage. The fill is genuinely `TRANSPARENT` since +036; while it overlapped the glyph it had to be filled with the row's own film colour, or the snowflake's arm ran through the digit. 26dp with a 1.5dp hairline carries a 16sp digit. **Rung 1 is the fork's YELLOW**, not a cool tint: the badge sits on a *thawed* snowflake, and giving it a colour of its own made an unfrozen row look half-frozen. The ladder proper starts at rung 2, where the freezing starts. The 盗み見 Freeze box uses the **same builder**: each step lights in its own rung, the master switch and the box frame wear the deepest rung standing. **Level 1 is not a freeze** — `FreezeUtils.isFrozen` is false for a merely stopped package and anything that opens it clears the mark — so it has an accent and a badge but **no film**, and its row stays an ordinary row; `freezeFilmKey(1)` returns null for exactly that reason. **Expect many ① badges**: `FLAG_STOPPED` is also set for an app that has never been launched since install, not only for one you force-stopped. `ApplicationItem.freezeLevel` is filled from the same live `getPackageInfo` that fills `isFrozen`/`isSuspendedApp` (match flags mandatory, or a hidden package resolves to nothing and every gate reads false); the stale-cache branch claims `GATE_DISABLE` at most, since disabled is all the DB knows. `MainCardBinder` derives the level from the item, else from the `ApplicationInfo`, and goes through the same `FreezeLevelBadge` — the +30 rule says those surfaces share colour keys, and sharing the builder is strictly better. **Retired with it**: `FREEZE_SUSPENDED`, `FILM_FROZEN` and `FILM_SUSPENDED` no longer paint anything, so their settings rows and legend entries are gone (the keys stay — they are in exported prefs files); `FREEZE_FROZEN` survives only as the fallback for a surface that cannot work the rung out. The suspended row keeps its **padlock** — shape reads further than colour at 26dp — but takes the ladder's accent, since suspension is no longer the deepest thing on the list. |
| **A level is a bulk action, and it is the only record of how a phone is frozen** (白い熊, +038) | `FreezeUtils.setLevel(pkg, userId, level)` plus `BatchOpsManager.OP_FREEZE_LEVEL_1..4`, four pills on the selection pane (`MainToolbarPrefs` keys `freeze_level_1..4`, ring icons `ic_freeze_level_N`). A level means **gates 1‥N applied and every gate above released**, so level 4 is exactly `freezeTotal` and the lower rungs are it truncated. **Order is load-bearing twice**: release runs first and top-down (a hidden package is reported as not installed, so nothing below gate 4 can be read or written while it stands), then apply runs bottom-up for the `freezeTotal` reason. A gate already in the wanted state is skipped rather than re-written — `setGate` would happily re-issue it, and a force-stop of an already-stopped app is a real kill while a re-suspend rewrites the suspending-package slot. **Success is `levelOf` afterwards, never the calls returning**, which makes it a test of the *top* gate: a PERSISTENT process that survives the force-stop under a disable gate still reads level 3, and that is the truth. **Four ops rather than one carrying a level** because `BatchOpsService.getDesiredOpTitle` is handed the op and nothing else — the notification, the operation bar and the history would otherwise all say only "Freeze". **The per-app remembered method is deliberately NOT written** (the +032 rule: the method is what the snowflake does next). `freezeTargetForOp` returns null for these, so `applyBatchOpResult` falls to the targeted re-read — right, because an optimistic snap would have to guess whether each gate landed, and the hide gate genuinely varies per app. **Why it exists (白い熊, 2026-09-12): the level is the ONLY thing that records how this phone is frozen, and it is not persisted anywhere** — `levelOf` reads it live off `ApplicationInfo` on every bind, the gates persist nothing, and the settings export carries only `shared_prefs/` + `files/profiles/` + `files/fonts/` (the per-app remembered method lives in the Room `freeze_type` table and does not travel; an app backup's `FreezeRule` carries that method but `RestoreOp` only `storeFreezeMethod`s it and **never freezes anything**). So the way to reproduce a phone's freezing is a **profile per depth** — profiles DO travel, as `Category.PROFILES` — filter the list to the profile, select all, tap the rung. That is the workflow these four pills were asked for. **The single-app pane carries the same four rungs (白い熊, +039)**, in place of its Freeze pill (`freeze` stays an `AppPanePrefs` key, hidden, so it can be brought back): there the rung the app is standing on is drawn **filled** — `AppPaneBinder.isLit`, off `ApplicationItem.freezeLevel`, the same number the row's badge shows, so pill and badge cannot disagree — and **tapping the lit rung releases to rung zero**, the shelf's own rule that one pill is both the way in and the way out. That is why `setLevel` takes **0**: it is a release, so it skips the 必要 guard and the freeze-myself guard (the way back must always exist) and lifts every gate including the force-stop, which `unfreeze` deliberately leaves alone. The pane goes straight to `setLevel` on a worker rather than through the batch service, as `toggleFreeze` does — one app is instant and a protected app's refusal is worth showing where the tap was — and it re-broadcasts `sendPackageAltered` **on the failure path too**, since a partial walk still moved the app. The snowflake under the icon still thaws, unchanged. **Labels are "Freeze ①‥④" and the pill leads with the snowflake (白い熊, +040)** — the circled digit is the badge the row draws, so pill and badge read as one thing, and it is in the *text* rather than as the leading glyph so it is not shown twice. **The gate's own name stays** (白い熊, +041, after it was briefly dropped in +040): a rung that does not say what it does is a number and nothing else, and the word is how you pick the right one without opening the freeze box. It does read close to the Force-stop pill beside it. **They are not the same action** — identical only on an app at level 0. On a frozen app, Force-stop adds gate 1 and leaves the freeze standing, while rung 1 tears every gate above it down; and on an app already at rung 1 (very common — `FLAG_STOPPED` is set for anything never launched since install) the lit pill *releases* the stopped flag, i.e. the opposite. Force-stop therefore stays: it is "kill this now without changing how frozen it is", which no rung can express. |
| **The four gates are four switches** (白い熊, +032) | `FreezeUtils.GATE_FORCE_STOP/SUSPEND/DISABLE/HIDE` (1–4, the step numbers the UI shows, in the order `freezeTotal` applies them) plus `isGateApplied`/`canOperateGate`/`setGate`, and the **Freeze sub-box** on the 盗み見 page (`view_freeze_box.xml` + `view_freeze_gate_row.xml`, bound by `AppDetailsSnoopingFragment.bindFreezeBox`). **Why it exists**: Android Auto refuses to run against a `FREEZE_TOTAL`-frozen Google Maps and runs happily against the same Maps carrying only the disable gate — measured 2026-09-12 on the second phone, where `dumpsys package com.google.android.apps.maps` reads `installed=true hidden=false suspended=false stopped=false enabled=3`, `lastDisabledCaller: 2000`. The discriminator is **installedness**: a disabled package is still listed by a plain `pm list packages` (verified) while its activities stop resolving (`cmd package resolve-activity` → `No activity found`), whereas a hidden one is reported as *not installed* and a presence check on it throws. Nothing in the app could express that state, because every freeze was a **method** — one value, applied wholesale — so the box gives each gate its own switch and 白い熊 can find the rung an outside app trips over by driving. **These are NOT a new freezing method and nothing persists them**: `FreezeUtils.isFrozen` is still the app-wide truth (suspend/disable/hide — *not* stopped, so a phone carrying only step 1 is a phone with nothing frozen and the master switch reads off), the `FREEZE_*` values are still the wire format, and the box is a second door onto the same platform calls. **The master switch is `FREEZE_TOTAL` on / `unfreeze` off and deliberately raises no method picker** — a switch that opens a dialog is not a switch — and it leaves the per-app remembered method alone, or it would silently change what the main list's snowflake does next. **`setGate` measures rather than infers**: it re-reads `ApplicationInfo` (with `MATCH_UNINSTALLED_PACKAGES \| MATCH_DISABLED_COMPONENTS`, or the hide gate resolves to nothing) and answers whether the state actually moved — a suspension lifted in the wrong slot returns looking like success, `hideBestEffort` reverts itself when the row would vanish, and a PERSISTENT process is back before the force-stop returns. **Step 1 needed a release that did not exist**: a force-stop leaves `stopped=true` and the only ordinary way out is launching the app, so `PackageManagerCompat.setPackageStoppedState` (guarded by `CHANGE_COMPONENT_ENABLED_STATE`, which this shell holds) is what makes it a two-way switch; `FreezeUtils.unfreeze` still does not clear it, and the master switch clears it separately. **Applying a gate goes through the 必要 guard; releasing never does** — an app added to the profile after it was frozen must still be thawable, which also fixed the old unfreeze path on this page. A gate this phone cannot operate keeps its number, name and explanation and loses only its switch (drawn at 0.55 alpha, its reason in place of the chip): the ladder is also the page's account of what a freeze *is*, and a rung silently missing explains nothing. **LANDMINE — `<include>` layout params**: `LayoutInflater.parseInclude` uses the `<include>`'s own `layout_*` whenever it can build them and falls back to the included root's only when that **throws**, which is what a missing `layout_width` does — so giving the freeze-box include a width/height would silently drop the card's `layout_marginTop`. The four step rows share every id inside them, so each row is resolved once in the view holder and every later lookup is scoped to the row. Replaced the card's "Suspend this app" row and its "Freeze" pill; uninstall stays as a half-width pill with a weighted spacer beside it. |
| **LANDMINE — a hidden app is invisible to a query that does not ask for it** (白い熊, +29) | `PackageManagerCompat.isPackageHidden` looked the package up **without** `MATCH_UNINSTALLED_PACKAGES`. A hidden package is *precisely* one the platform reports as not installed for the user (`PackageUserState#isAvailable` = `installed && (!hidden \|\| matchUninstalled)`), so that query threw `NameNotFoundException` for exactly the packages it was asked about, fell through to the `MANAGE_USERS` reader this phone's shell cannot use, and answered a flat **"not hidden"** — whereupon `FreezeUtils.unfreeze` skipped the reveal and **a hidden app could never be thawed again from the app**. Latent and harmless until +29, because nothing here had ever succeeded in hiding anything. The same trap governs every surface that can meet a frozen app: `AppDb`'s enumeration, `ApplicationItem`, `AppDataTransfer.isFrozen` and the battery screen already pass `MATCH_UNINSTALLED_PACKAGES \| MATCH_DISABLED_COMPONENTS`; **any new lookup must too**. Paired guard, because the row is the only way back: `hideBestEffort` re-reads the package after hiding through the **exact predicate the list uses** (`ApplicationInfoCompat.isInstalled`, which is what `App.fromPackageInfo` sets `App.isInstalled` from) and **reverts the hide** if the app would not get a row. Hiding sets `PRIVATE_FLAG_HIDDEN` and leaves `FLAG_INSTALLED` alone, so by construction the row survives — but this phone had never once executed a hide, so the assumption was untested and is now checked rather than trusted. `revealBestEffort` is the single place that knows both doors (shell, then delegate) and is used by unfreeze and by the revert. |

| **Three apps can never be frozen, suspended or uninstalled** (白い熊, +139) | `ProtectedAppsProfile.ALWAYS_PROTECTED` — 白い熊 雫, 白い熊 応用管理, 白い熊 自由作業盤 — checked **before** the profile lookup, so the answer never depends on the profiles being readable. The 必要 guard fails *open* by design, which is right for a list you edit and wrong for the apps that make this one work: the moment the profiles cannot be read is exactly when a mistake becomes unrecoverable. | **Suspension is invisible to the main list unless we say so** (白い熊, +81) | **LANDMINE — suspending a package emits no `ACTION_PACKAGE_CHANGED`.** The main list is never polled: `MainViewModel.onResume` re-filters only when the *Running apps* filter is on, and everything else arrives by broadcast. The platform sends `ACTION_PACKAGES_SUSPENDED` (which `PackageChangeReceiver` does listen for) and it did **not** reach us on the Mate XT — so an app suspended from the Snooping card kept the state its row was built with. That is not merely a stale label: the running box is gated on `!item.isFrozen`, so a row that never learned it was frozen also kept its **orange “running” frame** for an app the system had stopped dead. Fix: every successful policy write that changes what the list shows calls `BroadcastUtils.sendPackageAltered(...)` — the mechanism the rest of the fork already uses for its own writes, and the receiver lives on the **view model**, so it is heard while another activity is on top. Add that call to any new write here. **Second landmine, same feature:** the platform records suspension **per suspending package**, so `PackageManagerCompat.suspendPackages(..., false)` as the shell cannot lift one applied under 雫's admin — the main-list snowflake would silently do nothing for ever. `FreezeUtils.unfreeze` therefore ends with a best-effort `DevicePolicyBridge.setSuspended(pkg, false)`. Display: `ApplicationItem.isSuspendedApp` is the cheap flag filled from the same live query as `isFrozen` (**not** the `isSuspended()` method beside it, which does a lazy `fetchPackageInfo()` — far too expensive per row at bind time); the row keeps the italic and gains a violet **padlock** in place of the snowflake, a **struck-through label**, and a heavier violet film (`ColorPrefs.FREEZE_SUSPENDED` / `FILM_SUSPENDED`). The suspended branch is tested **before** `isFrozen` everywhere, since suspended implies frozen. |
| **LANDMINE — any enabled-state change of `com.huawei.lbs` kills `system_server`** (白い熊, measured 2026-11-19) | EMUI bug, not ours. `HwLocationProviderProxy`'s `PackageMonitor.onPackageChanged` answers every `PACKAGE_CHANGED` for `com.huawei.lbs` with `startServiceWatcher` → `ServiceWatcherImpl.register`, whose `checkState` throws `IllegalStateException` because the watcher is already registered; it is thrown on `android.bg`, so the system process dies and the phone soft-reboots. Reproduced from the shell with a bare `pm enable --user 0 com.huawei.lbs` (17:24:54), and the same trace sits behind the three reboots 白い熊 got from the app that day. **The write does not survive**: the crash comes before the package restrictions are flushed, so the package is still `enabled=3` afterwards — an unfreeze here cannot succeed, it only reboots. Separately, `pm unsuspend` from the shell answers `new suspended state: true`: the suspension is owned by `android`, not by the shell, so the shell cannot lift it. The stack trace is **not** in dropbox (`contents lost`) — read it with `logcat -b crash -d`, which survives the soft reboot. `install-existing` (PACKAGE_ADDED) did not crash. **The way out that worked (17:31:54):** enable it in the first instant of the restarted system, before Huawei's watcher is listening — from one `adb shell`, run `cmd package enable --user 0 com.huawei.lbs` (this one crashes the system), then spin on the same command until it answers `new state: enabled` (try 338, three seconds later, on the new `system_server`). No broadcast reaches the proxy, the write is flushed, and the package stays `enabled=1`. `pm disable-until-used` is refused for the shell (`Shell cannot change component state … to 4`). |
| **Every enabled-state write goes through the guard** (白い熊, +121) | `FreezeUtils.setEnabledStateGuarded` is the one place this app calls `PackageManagerCompat.setApplicationEnabledSetting` (four former call sites: `freeze`, `freezeTotal`, `unfreeze`, `setGate`). For a **system app** it first arms `utils/EnabledStateGuard`: a detached script (`setsid sh -c …`, started through `Runner`, so shell uid and outside the app world) that watches `pidof system_server` for a few seconds, exits if it survives, and otherwise spins on `cmd package enable|disable-user` until the restarted package service accepts it — the recipe in the row above, automated. Files live in `<external files>/state-guard/`, never `*.log`: `pending-<pkg>.txt` (app-written before the change, withdrawn 3 s after the call returns, **without blocking** — a batch over many system apps must not wait per app), `<pkg>.txt` (script-written only when it stepped in, retried until storage is back) and `seen-<pkg>.txt` (a report already shown = the record of packages known to restart the system; no prefs file, so nothing to classify in `SettingsBackupManager`). `MainActivity.showStateGuardReports` reads them on every resume, on a worker, and waits out a 3-minute grace before calling a marker with no report a failure. `MainRecyclerAdapter.confirmSystemRestartRisk` asks before a system app crosses the disable gate from the pane rungs or the snowflake: always for a known package, otherwise only on the way in. **Not covered by a question** (the guard still covers them): batch ops, the app-details freeze, the gate switches on the 盗み見 page. Verified without a crash: script syntax and its 9-second survive-and-exit path, the shell's write into our external files directory (`shell:ext_data_rw 0660`), `setsid` present. **Unverified until tried on `com.huawei.lbs`:** that a script started through the server survives the restart, and that the disable direction crashes at all. |
| **`com.huawei.lbs`: the enable crashes only in some system lifetimes** (白い熊, measured 2026-11-19, +121) | After a **full boot at 17:38:51 with the package enabled**, freezing it to level 3 (18:08) and thawing it again (18:10) in that same lifetime crashed **nothing**: `enabled=3` → `enabled=1`, same `system_server` pid, empty crash buffer, the guard armed and stood down both times. So two readings are still open and were not separated: (a) the watcher is registered at start only when the package is disabled then, and a later enable registers it again; (b) a soft restart leaves something a full boot clears. Settle it with: freeze to level 3, **full reboot**, thaw. That is also the first real test of the guard, which has so far only ever stood down. |
