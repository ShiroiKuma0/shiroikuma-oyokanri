`snooping/` — catalogue, resolver, levers, enforcer, tri-state, drift, activity times — and `trackers/`. Device-policy hard locks are in `device-policy.md`.

| Anti-snooping tab (`snooping/` + app details) | Fork tab **Snooping / 盗み見**, displayed **second, right after App info**, listing every privacy-invasive capability of the app that ADB/Shizuku can *actually* switch off. **Display order is decoupled from the property id**: `AppDetailsFragment.SNOOPING` is **13** (appended, never inserted — those ids key the view model's per-property state) and `AppDetailsActivity.TAB_PROPERTIES` maps tab position → property; that array and `R.array.TAB_TITLES` must stay the same length and order. Catalogue = `snooping/SnoopingCatalog.java`: entries name their app-op by **AOSP name** (`"FINE_LOCATION"`), never by numeric code (codes are renumbered between releases), resolved against the running platform by walking `0.._NUM_OP` and asking `opToName`. Each entry's `id` is a **stable wire key** persisted + exported — **never rename one**. Three tiers, all computed on-device, never hardcoded: **requested** (app declares the permission, or the op is at a non-default mode), **ungated** (`AppOpsManagerCompat.opToPermission(op) == null`, i.e. the app can use it without declaring anything — screen capture, clipboard, assistant reads, VPN, background run) — both shown by default — and **not-requested** (permission-gated, app never asked), hidden behind ⋮ → *Show all* as a pre-set that lands when a future update starts asking. **LANDMINE — `opToSwitch`, verified on-device 2026-07-27:** `AppOpsService` runs every write through `AppOpsManager.opToSwitch(op)` **before storing it**, so an op whose switch op is a *different* op has **no slot of its own** — the write silently lands on the controlling op and the row can never move (for us, for `adb`, or for root). Proof: clearing `COARSE_LOCATION` then writing `GPS = ignore` produced `COARSE_LOCATION: ignore`, while `GPS` still read "No operations. Default mode: allow"; same for `MONITOR_HIGH_POWER_LOCATION`. `SnoopingCatalog.isIndependentlySettable(op)` therefore drops **any** op where `opToSwitch(op) != op` — a rule, not a list, so a capability merged on one Android version and split on another needs no maintenance. **LANDMINE — stored mode ≠ enforced mode:** the per-op entry from `getOpsForPackage` is *absent* until something writes it, so a row built on it defaults to `opToDefaultMode` and claims "Allowed" for capabilities the system already denies. `AppDetailsSnoopingItem.refreshEffectiveMode` reads `checkOperation` (which resolves uid modes + op switching) instead; `isAllowed()` prefers it and falls back to the stored mode only when the platform refuses to answer. Same gap broke *writes*: `PermUtils.setAppOpMode` returns early when `checkOperation` already equals the target, which silently swallowed `PHONE_CALL_MICROPHONE`/`PHONE_CALL_CAMERA` in +6 — so ungated/pre-set rows now call `appOpsManager.setMode` **unconditionally** (rows with a real modifiable permission still go through `AppDetailsAppOpItem.allowAppOp`/`disallowAppOp`, which moves permission + op + flags together). A **not-requested** row must move the **op alone** — granting/revoking a permission the app never declared throws and would lose the pre-set. **LANDMINE — uid mode vs package mode, measured on-device 2026-07-27 (+8):** `AppOpsManagerCompat.setMode` writes the **uid** mode on Android M+ (`setUidMode`) while `adb shell appops set <pkg> <op> <mode>`, other tools, and older builds of this fork write the **package** mode — a different slot. `AppOpsService` **deletes** an entry whose mode equals `opToDefaultMode` instead of storing it, so *un-blocking* an op whose default is `allow` (e.g. `PHONE_CALL_CAMERA`) cleared a uid entry that never existed while the package-level `ignore` kept winning: `checkOperation` still answered `ignore`, the switch stayed off, nothing threw, and the decision was recorded anyway → the row read **"Blocked · saved: allow"**. Proof: `appops set --uid … PHONE_CALL_CAMERA ignore` adds `PHONE_CALL_CAMERA: mode=ignore` under `Uid u0a…:`; writing `allow` (its default) makes that line vanish with the package entries untouched. Fix = `AppOpsManagerCompat.setModeBothLevels` (uid first, then package best-effort — correct in all four default/target combinations), plus `AppDetailsSnoopingItem.repairIfUnchanged` (forces the package entry when the enforced mode did not move, so the permission path keeps its `MODE_FOREGROUND` nuance unless it demonstrably failed). **Store only departures from the default (白い熊, +13).** `AppDetailsSnoopingItem.defaultAllowed()` resolves the untouched state from `opToDefaultMode` (`MODE_ALLOWED`/`MODE_FOREGROUND` → allowed, `IGNORED`/`ERRORED` → blocked, `MODE_DEFAULT` → the linked permission decides, so dangerous ⇒ blocked, otherwise **null = unknown**); `isDefaultState(allowed)` gates the write, and a toggle back to the default **`clearSetting`s** the row rather than storing it — otherwise the enforcer would keep re-asserting a no-op and it would travel in every export as noise. `blockAllSnooping` must do the same *and* clear such ids explicitly, because `SnoopingPrefs.setSettings` only merges. **Null means "store it"** — a redundant record is harmless, a dropped one is not. The row's status line therefore says **nothing** about the stored decision (it would only restate the switch); what marks a row instead is **one accent colour driving both the card stroke and the switch** (+14/+15): **red `#ff0028` whenever the capability is allowed** (the app can do it right now), **yellow `ForkThemeUtils.getTextColor()` when it is blocked but the platform default is allow** (you closed it), **grey = the card's own `defaultStrokeColor` when it is blocked and blocked is the default** (nothing to look at). The **3dp stroke is drawn only when `isChangedFromDefault()`** — an allowed-by-default row gets a red switch but no frame. The switch takes the accent on `setThumbTintList` + `setTrackDecorationTintList` (dot + outline) with `setTrackTintList` transparent so it stays hollow in every state; `MaterialSwitch` (material 1.13) is the only widget with `trackDecoration`. The "Allowed" pill is a **filled blood red `#6E0B14` with near-white `#FFD9DC` text** (a wash was too bland for the state that matters); "Blocked" stays a green wash — the only tell for the case that has no other one, a capability that is ON by default and off only because you turned it off. Capture `card.getStrokeColor()`/`getStrokeWidth()` in the ViewHolder ctor and restore them in the else branch (recycling); both are plain fields, unlike `getRadius()`. **Never record a decision a write did not achieve:** `matchesRequestedState(requested)` re-reads `checkOperation` and both `setSnoopingAllowed` and `blockAllSnooping` skip the `SnoopingPrefs` write when it disagrees (it returns `true` when it *cannot* tell, so only a positive contradiction counts as failure). The **status chip is the handle for the saved decision** — tapping it (only when one exists) opens the same dialog as a long-press, with *Forget this setting*. **Inclusion rule (白い熊, +10/+11): the page shows only what is snooping now, or what can be *made* to snoop.** Three filters serve it. **(1) Reachability — `snooping/SnoopingReachability.java` (+11), the cheap one, and the one to extend first:** judged from the app's own manifest on every load, no writes and nothing persisted, so an update that adds the missing declaration brings the row back by itself. Per-capability prerequisites, and *only* where unambiguous: `media_*_read` → a `READ_MEDIA_*`/`READ_EXTERNAL_STORAGE`/`MANAGE_EXTERNAL_STORAGE` declaration; `microphone_hotword`+`microphone_call` → `RECORD_AUDIO`; `camera_call` → `CAMERA`; `sms_write` → any SMS permission (no SMS permission ⇒ cannot hold the default-SMS role); `device_identifiers` → system/privileged or `READ_PRIVILEGED_PHONE_STATE` (signature-only since Q); `accessibility`/`vpn`/`assist_*` → a `<service>` whose `android:permission` is the matching `BIND_*` (assist also accepts an `ACTION_ASSIST` activity, found via `queryIntentActivities`). **Fails open everywhere** — unknown id, or any thrown lookup ⇒ reachable. **LANDMINE (cost build +11):** `PackageInfo.services` is `null` for **two** different reasons — the caller omitted `GET_SERVICES`, *or* the app declares no services at all. The first is "no data" (fail open), the second is the strongest possible evidence of unreachability (fail closed), and a `PackageInfo` cannot tell you which. Treating both as "no data" left every service-gated row on the page for exactly the apps that most deserved to lose them (8 rows instead of 4 for a zero-service app). `SnoopingReachability.services()` therefore **re-queries with `GET_SERVICES | MATCH_DISABLED_COMPONENTS` when it sees a null** and only a *thrown* query counts as unknown. Same trap applies to `activities`/`receivers`/`providers` if a future rule uses them. Capabilities with no manifest gate at all (`PROJECT_MEDIA`, `READ_CLIPBOARD`, `RUN_*_IN_BACKGROUND`) can never be hidden this way. For a zero-permission app this drops 12 of the 16 ungated rows. **(2) Learned marks — `SnoopingImmovable`, the backstop** for refusals no manifest explains: `isModifiable()` is a privilege check, not a per-op one, so a row that is blocked and refuses to move was still rendered as a dead switch. The platform cannot be asked in advance (it accepts a write and discards it), so it is learnt: when a *turn-on* write leaves `checkOperation` unchanged, `snooping/SnoopingImmovable.java` marks `pkg`+`id` and `SnoopingResolver` drops the row. **A mark only hides a row that is currently BLOCKED** — a stale mark can therefore never conceal actual snooping, only omit a safe row. Own prefs file `shiroikuma_snooping_immovable.xml`, listed in `SettingsBackupManager.EXCLUDED_PREFS` (a fact about this phone's app-ops behaviour, not a decision — carrying it to another phone would hide a capability that is movable there). Self-healing: `SnoopingInstallReceiver` calls `clearPackage` on `PACKAGE_ADDED` and `clearAll` on `MY_PACKAGE_REPLACED` (a new build may write app-ops differently — +9 did), and *Show all* reveals them. **(3) Writability of a permission-only row — `SnoopingResolver.canWritePermission`, measured on-device 2026-07-28 (+17).** `location_background` (`ACCESS_BACKGROUND_LOCATION`) is the catalogue's only `Entry.perm`: no app-op exists for it on any release, so the permission itself is the lever. `AppDetailsPermissionItem.modifiable` = `PermUtils.isModifiable`, which asks about **our** privileges and the protection level and says nothing about the app the write lands on — and `PermUtils.revokePermission` branches on `supportsRuntimePermissions(applicationInfo)` (`targetSdkVersion > 22`): a **legacy app takes the compat branch, which can only act through the app-op** and never clears the grant itself, so for a permission with no op the branch does nothing, `permission.isGranted()` is still true when `persistChanges` runs, and it promptly **re-grants** what you asked it to revoke. Proof: `com.polyclock` (複数時計, target SDK 22) → `ACCESS_BACKGROUND_LOCATION: granted=true, flags=[REVOKED_COMPAT|REVOKE_WHEN_REQUESTED|…]`, switch immovable for us and for anything else. So a permission-only row is dropped unless `PermUtils.supportsRuntimePermissions(app) || permission.affectsAppOp()` — the platform's own rule, so a modern app keeps its working switch and an app that raises its target SDK gets the row back with no maintenance. Paired fix: `matchesRequestedState` used to return `true` for *every* permission-only row (op-less ⇒ "no evidence"), so a refused revoke was recorded as a success; `AppDetailsSnoopingItem.refreshEffectivePermission` now re-reads `PermissionCompat.checkPermission` after the write — **and consults the op when `affectsAppOp()`**, because a legacy compat-revoke deliberately leaves the grant in place and only moves the op, which a bare `checkPermission` would misread as a failed write. The "needs no permission" suffix keys off `capability.isUngated()`, **not** the tier: keying it off `TIER_UNGATED` made the label disappear the moment an op got an explicit non-default mode (which promotes the row to `TIER_REQUESTED`), so blocking a row silently changed what it claimed about itself. Store: `snooping/SnoopingPrefs.java` → own prefs file `shiroikuma_snooping.xml`, key `pkg:<packageName>`, value `id=0/1` pairs; absence is a real third state (*not managed*), unknown ids survive read-modify-write. Because it is its own `shared_prefs/*.xml` it flows into Export/Import as `Category.SNOOPING` (wire id `snooping`) with no serialisation of its own. Replay: `snooping/SnoopingEnforcer.java` — `SnoopingInstallReceiver` (manifest-registered `PACKAGE_ADDED`, one of the implicit broadcasts still delivered on O+, plus `MY_PACKAGE_REPLACED`) and a sweep from `Ops.setAuthenticated(ctx, true)`, the one point where privileges are settled; without privileges nothing is dropped, only deferred to the next launch. `snooping/SnoopingResolver.java` is the **single** place deciding what the tab shows, shared with the enforcer so replay can never disagree with the UI. **Beyond app-ops (白い熊, +18).** The ops turned out to be the easy half; the capabilities that matter most are gated elsewhere, so a row now has **three possible mechanisms** and `SnoopingResolver` picks one: op → permission-only → **lever**. A lever (`snooping/lever/`, registry `SnoopingLevers` keyed by the same stable wire id) answers `isApplicable`/`isModifiable`/`isAllowed`/`setAllowed`/`defaultAllowed`/`detail`, and `setAllowed` must **return whether the platform actually did it** — the caller records nothing otherwise. Five exist: **`network_internet`** (per-uid net policy; `INTERNET` is install-time so it can never be revoked — the *strongest available* reject bits are discovered by reflecting over `NetworkPolicyManager`'s own fields, strongest-first `POLICY_REJECT_ALL` → `POLICY_NETWORK_ISOLATED` → `REJECT_WIFI+REJECT_CELLULAR` → AOSP's `POLICY_REJECT_METERED_BACKGROUND`, and the row's detail chip **names the rung** so the switch never claims more than it does), **`accessibility_service`** + **`notification_listener`** (the colon-separated `Settings.Secure` lists — `enabled_accessibility_services` with `accessibility_enabled` following it down, and `enabled_notification_listeners`; the `ACCESS_ACCESSIBILITY`/`ACCESS_NOTIFICATIONS` **ops are not these gates** and are kept as separate rows), **`assistant_role`** (`cmd role {get,add,remove}-role-holder android.app.role.ASSISTANT` **and** the older `Settings.Secure` `assistant`/`voice_interaction_service` pair — both are read, blocking clears both), **`battery_exemption`** (`DeviceIdleManagerCompat`; both compat methods return `true` for cases they did not change, so the state is always re-read). **LANDMINE — secure settings cannot go through `Settings.Secure.putString`:** that runs in *our* process under *our* uid and 応用管理 holds no `WRITE_SECURE_SETTINGS` (`ActivityManagerCompat.startActivityViaAssist` has to `requireSelfPermission` it), so every write goes through `Runner` (`settings put --user <id> secure …`, `settings delete …` for an empty list — `put ''` stores a literal empty string on some builds). Reads use the in-process `Settings.Secure.getString` only for **our own user** and the shell for any other. A failed *turn-on* **never marks a lever row immovable** (`item.lever == null` guard in `setSnoopingState`): an a11y service or assistant role we could not restore is one the user can still restore from Settings, so hiding it would hide something that may come back. **Tri-state (`snooping/SnoopingState.java`).** Rows are now `BLOCKED=0`/`ALLOWED=1`/`FOREGROUND=2` — the numbers are the **wire format** in `shiroikuma_snooping.xml`, so 0/1 must keep their meaning forever and an unknown value decodes to BLOCKED. `SnoopingPrefs` therefore stores `Map<String,Integer>`, and the item exposes `getState`/`setState`/`supportedStates`/`nextState`; **tapping a card advances to the next state it supports**, long-press lists them explicitly. `supportsForeground()` is restricted to op rows with a **dangerous runtime permission** — `AppOpsService` will happily store `MODE_FOREGROUND` for any op, but only where the framework consults the uid's process state does it mean anything, and a third position that silently behaved like "blocked" is worse than not offering it. When the permission path is taken, `allowAppOp` puts the op at `MODE_ALLOWED` first, so FOREGROUND **re-narrows the mode afterwards** at both levels while leaving the grant in place. The switch is on for both allowed states (a switch has two positions and the row has three); the state is read from the **theme yellow** pill/stroke — `ForkThemeUtils.getTextColor()` via `statusColorForeground()`, **not** the old hard-coded amber `#FFC24B` (白い熊, +56: the fork has one yellow, and it is the configurable theme's). It therefore shares a colour with "blocked by us", and the two are told apart by the pill's words — a narrowed row names its own rung, e.g. "No background mobile data". **Components (`snooping/SnoopingComponents.java`).** One place resolves capability id → the `ComponentName`s behind it (a11y, NLS, VPN, voice-interaction + `ACTION_ASSIST` activities); the long-press *Disable / enable the component* action drives `PackageManagerCompat.setComponentEnabledSetting(DISABLED_USER)` — the blunt instrument and the only answer for a capability with no op, deliberately **not** recorded in `SnoopingPrefs` (component state is the Blocking feature's territory and survives on its own). `SnoopingReachability` now delegates its `services()` to this class, and the lookup is **memoised in a `WeakHashMap` keyed by the `PackageInfo` instance** — one resolve pass would otherwise re-query the package manager once per component-bearing capability. **Catalogue completeness:** ⋮ → *Ops not in the catalogue* (`SnoopingCatalog.missingOpNames()` + `AppDetailsViewModel.getUncataloguedOps`) walks `0.._NUM_OP`, drops what `isIndependentlySettable` rules out and what is already listed, and shows/logs the rest with this package's current mode — so extending the catalogue is reading a list rather than remembering one. **Group order is by consequence, not subsystem** (`Group` enum order *is* render order and nothing persists it): NETWORK → ACCESSIBILITY → SCREEN_WATCHING → LOCATION → MIC_CAMERA → MESSAGING_CALLS → PERSONAL_DATA → STORAGE_MEDIA → NEARBY → BACKGROUND. **All-network block (白い熊, +19).** The metered-background policy is the *narrow* rung — measured on the Mate XT, `Metered ifaces: {rmnet0}`, so on WiFi it cannot fire at all — so `network_internet` is now **three-state**: ALLOWED → `FOREGROUND` = the net policy (labelled **"No background mobile data"**, never "Only while in use" — a lever names its own states via `SnoopingLever.stateLabelRes`, because the generic label would misdescribe it) → BLOCKED = a **per-uid firewall DENY on every interface**, via `ConnectivityManagerCompat.setUidFirewallRule` (the compat class and the `IConnectivityManager` stubs already existed upstream). **Chain = `FIREWALL_CHAIN_OEM_DENY_2`**: the AOSP chains (dozable/standby/powersave/restricted/low-power-standby) are driven by `AppStandbyController`, which rewrites their rules on every bucket change and would silently undo ours; the three `OEM_DENY` chains exist for exactly this and AOSP never touches them (`_2` rather than `_1` on the assumption an OEM helping itself takes the first). `setFirewallChainEnabled(chain, true)` is asserted on every block — idempotent, and unreadable before Android 14. **Privilege: shell holds `NETWORK_SETTINGS`** (verified on-device 2026-07-28: `NETWORK_SETTINGS`/`MANAGE_NETWORK_POLICY`/`CONNECTIVITY_INTERNAL` yes, `NETWORK_STACK` no), which is what `ConnectivityService.setUidFirewallRule` accepts. **LANDMINE — the rule is write-only on Android 13:** `getUidFirewallRule`/`getFirewallChainEnabled` are U+, and no `dumpsys` shows chain membership, so the tab's "always re-read what the platform enforces" discipline has nothing to ask. `snooping/NetBlockState.java` (own prefs `shiroikuma_netblock.xml`, in `EXCLUDED_PREFS` — device-local, and uids do not travel) records writes that **returned without throwing**, which for *this* API is real evidence (it throws `SecurityException`/`ServiceSpecificException` on refusal, unlike `AppOpsService`, which accepts and discards); Android 14+ asks the platform instead. It stores the **uid** alongside the package because a reinstall changes it, and unblocking clears the rule for the *recorded* uid as well as the current one, or a stale DENY outlives the app and lands on a recycled uid. The policy rung is applied *alongside* the firewall block, not instead of it, so a flushed chain still leaves the weaker protection. **Ops added from the on-device report** (+19, the `missingOpNames()` feature paying for itself — 50 uncatalogued on Android 13): `ACTIVATE_PLATFORM_VPN`, `MANAGE_IPSEC_TUNNELS`, `BIND_ACCESSIBILITY_SERVICE` (a second, independent gate beside the secure-settings list), `LOADER_USAGE_STATS`, `RECORD_INCOMING_PHONE_AUDIO`, `RECORD_AUDIO_OUTPUT`, `SMS_FINANCIAL_TRANSACTIONS`, `USE_ICC_AUTH_WITH_DEVICE_IDENTIFIER`, `CALL_PHONE`, `QUERY_ALL_PACKAGES`, `INTERACT_ACROSS_PROFILES`, `NO_ISOLATED_STORAGE`, `CHANGE_WIFI_STATE`. The report now filters op names starting with `deprecated` (the framework keeps retired codes as placeholders to hold the numbering). **LANDMINE — `checkOperation` never answers `MODE_FOREGROUND` (白い熊, +20, cost a build):** `AppOpsService` runs the stored mode through `UidState#evalMode` before returning it, resolving foreground into ALLOWED or IGNORED **according to the app's process state at that instant**. So the enforced mode is the right source for "can it do this right now" and the wrong one for "what did we set": a row narrowed to foreground read back as BLOCKED whenever the app happened to be backgrounded, `matchesRequestedState(FOREGROUND)` was permanently false, and — because the old guard treated any failed *allowed-ish* request as "will not turn on" — the row was marked `SnoopingImmovable` and **vanished from the page** with the "cannot be turned on here" toast. Two fixes, both needed: `getState()` reads the **raw stored mode** (`opItem.getMode()`, uid entry then package entry via `getOpsForPackage`) and reports FOREGROUND from it *before* consulting `checkOperation`; and the immovable mark now requires `state == ALLOWED && !isAllowed()` — a refused **narrowing** says nothing about whether a capability can be turned on. (A stale mark is self-healing: `SnoopingInstallReceiver.clearAll` on `MY_PACKAGE_REPLACED` wipes them when this app is updated.) **Dialogs: `utils/ForkDialog` is the shared entry point** — `builder(ctx)` (yellow-on-black overlay pinned explicitly) + `present(builder)` (create → show → border) or `bordered(dialog)` for the call sites that do not own the `show()`, i.e. `DialogFragment.onCreateDialog` and dialogs whose buttons are re-wired after `create()`. `UIUtils.presentWithYellowBorder`/`yellowOnBlackDialog` are the older equivalent pair, still used by the snooping/battery screens; the monitor keeps its own private copy. **The border is never inheritable from a theme**: `MaterialAlertDialogBuilder.create()` rebuilds the window background as a stroke-less `MaterialShapeDrawable`, so `UiUtils.applyForkDialogBorder(dialog)` (driven by the `forkDialogBorderDrawable` attr on the dialog overlay, and a no-op wherever the attr is unset) must run afterwards — which is why **every libcore builder (`Searchable*`/`TextInput*`/`Scrollable`) is already bordered while a plain `new MaterialAlertDialogBuilder(ctx).…show()` is not**, no matter how fork-themed the host activity is. That asymmetry is what made the backup **delete-confirmation** dialog (and ~35 others) render borderless until +55 swept them; when adding a dialog to a yellow-on-black screen, route it through `ForkDialog` or it will silently be the odd one out. **Component disabling was tried and removed (白い熊, +18 → +23).** A row action, then a fourth state `COMPONENT_OFF = 3`, then nothing: **LANDMINE — shell cannot change component state at all** (measured on-device 2026-07-28). Since Android O the platform refuses it for anything that is not a **test-only** app; `pm disable <pkg>/<cls>` answers `SecurityException: Shell cannot change component state for … to 2`. Upstream's `SelfPermissions.canModifyAppComponentStates(userId, pkg, testOnly)` already encodes exactly this — consult it before building anything on `setComponentEnabledSetting`. The whole feature is gone from `SnoopingState`, `AppDetailsSnoopingItem`, `SnoopingResolver`, the fragment and the strings; wire value `3` is retired and decodes to `BLOCKED`. `SnoopingComponents` stays, minus its `forCapability` entry point, because `SnoopingReachability` and the levers still need the component lookup. **Also not a lock even where it works:** an app **can re-enable its own components** programmatically (`PackageManagerService.setEnabledSetting` permits a same-uid caller), so the strongest per-component action would never have been the hard block it looked like. **LANDMINE — a permission-backed op's mode is NOT independently settable (白い熊, +22, measured on-device 2026-07-28).** `PermissionPolicyService` re-derives the op mode from the permission grant and re-asserts it, so a direct write to such an op is accepted and thrown away. Proof on `org.localsend.localsend_app`: `cmd appops set <pkg> READ_EXTERNAL_STORAGE ignore` → still "No operations. Default mode: allow"; `set --uid … foreground` → stored as **`ignore`**; and on a package whose `CAMERA` permission is denied, a `--uid … CAMERA allow` write was back to `ignore` within one command. This is *why blocking works anyway* — `AppDetailsAppOpItem.disallowAppOp` revokes the permission and the policy service then agrees with us — and why `AppDetailsSnoopingItem.supportsForeground()` is now **hard-coded false for op rows**: `MODE_FOREGROUND` can never be written onto a permission-backed op. The platform's real "only while in use" is expressed by the **permission**, not the op (grant `ACCESS_FINE_LOCATION` without `ACCESS_BACKGROUND_LOCATION` and the policy service sets `MODE_FOREGROUND` itself) — which is the `location_background` row this tab already has; camera and microphone have no such permission pair at all, their "while using the app" being enforced by process capabilities with nothing to set. **Only the network lever keeps a middle rung**, because its middle state is a genuinely different mechanism (a per-uid policy) rather than an op mode. The `FOREGROUND` branches in `applyCapabilityState`/`modeFor` are kept — they are correct if the platform ever grows a settable foreground — and only the *offer* is withdrawn. Note the corollary for **ungated** ops (no permission behind them — clipboard, screen capture, background running): those have no policy service to fight and direct mode writes work, which is why those rows have always behaved. |
| **Accessibility is shown unconditionally** (白い熊, +68) | `ACCESS_ACCESSIBILITY` used to be gated in `SnoopingReachability` on the app declaring a `BIND_ACCESSIBILITY_SERVICE` service, and measurement supported the rule (on the Mate XT, all ten packages that had ever exercised the op declared such a service, and six of the seven with the op blocked declared none — those blocks predate +11). It is off anyway: this is the capability that subsumes every other on the page, the op costs nothing to block, and a manifest rule that is right about today's APK still hides the row from the app that adds the service in its next update. Being wrong here is not symmetric. **Catalogue additions in the same build:** `install_packages`/`delete_packages` (`REQUEST_INSTALL_PACKAGES`/`REQUEST_DELETE_PACKAGES`, Personal data — their permissions are `normal`, so `PermUtils` takes the read-only branch and moves the **op alone**, never attempting to revoke an install-time permission), `sip_calls` (`USE_SIP`, Messages & calls), and `read_logs` — the **second permission-only row** after `location_background`, working for the same structural reason: `READ_LOGS` is `signature\|privileged\|**development**`, and the development flag is what makes it revocable (it builds as a `DevelopmentPermission`, `readOnly=false`, so `PermUtils` acts on the grant itself). |
