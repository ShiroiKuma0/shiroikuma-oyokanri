| Settings export/import | Category-based (Kōjiki flow), on the **Export/Import section at the top of the 白い熊 応用管理 UI page** — the old "Settings export / import" category on the Backup/restore page is gone. `settings/SettingsBackupManager.java` bundles `shared_prefs/*.xml` + `files/profiles/` + `files/fonts/` (zip layout unchanged, so pre-category archives still import); its `Category` enum (GENERAL/APPEARANCE/MONITOR/TOOLBAR/NOTES/PROFILES) classifies every entry by prefs-file name on both export and import (`classify` — unlisted files fall into GENERAL, so nothing is ever dropped), and each carries a **stable wire `id`** (`general`/`appearance`/…) that the automation contract's `items` extra accepts — **never rename those**. The **archive name follows the family convention** (白い熊, 2026-07-25): `shiroikuma-oyokanri_<yyyy-MM-dd_HH-mm-ss>.zip` — no version, no infix, no suffix, because every sister app's backups share one directory; the pre-convention `AppManager-settings_` prefix survives only as `LEGACY_EXPORT_PREFIX`, still matched by the "last export" query. `writeExport(context, categories, OutputStream, ProgressListener)` is the **headless core**; the panel and `StateExportReceiver` are its two thin callers (never duplicate export logic in a caller). `settings/SettingsExportImportPanel.java` is the panel: bordered black/yellow box (transparent dialog window), tappable export-directory box (plain-path browser `settings/DirectoryChooserDialog.java`, shared with the backup-dir pref), a "Last export:" line (newest export zip by mtime; warn-red when unset/empty — also shown in the UI-page row summary, re-queried on page open + panel close), Select-all + category checkboxes, and an ArcaneChat pill row (Cancel left, Import/Export right). Success info dialogs are bordered; acknowledging them (OK on export, "Later" on import) **closes the whole chain** — info dialog → panel → UI page (back-dispatcher); "Restart now" hard-kills via `Process.killProcess(myPid)` — **not** `Runtime.exit` — or cached `SharedPreferences` will clobber the imported files on orderly shutdown. Failures (toast) leave the panel open. | **An import may TIGHTEN a security setting and never loosen one (白い熊, +117).** `settings/SecurityPrefGuard.java`: import replays whole prefs files, so an archive — months old, from another phone, or handed over by someone else — could switch off the app lock, turn off install verification or disable backup encryption, and a wholesale file copy could never notice. Guarded: `enable_screen_lock`, `enable_auto_lock`, `installer_disable_verification`, `installer_block_trackers`, `log_viewer_omit_sensitive_info` (booleans, each with the value that IS the safe one) and `encryption` (safe = **any** mode but `none`, so switching AES→PGP is a choice and AES→none is not). **The asymmetry is the design**: a setting is held only when the CURRENT value is the safe one and the archive would move it away — **including by omitting it**, since a missing entry reverts to the default and the default is not always safe (`encryption` defaults to `none`). A tightening always passes. **LANDMINE — it must edit the FILE, never the SharedPreferences API**: import replaces prefs files while the process still holds them cached (which is why "Restart now" hard-kills), so any `edit().apply()` here would write the cached map back over the file just imported and undo it; the correction is targeted regex surgery on the XML entry on its way to disk, inserting the entry when it is absent, and any unexpected shape passes the bytes through unchanged — a guard that breaks an import is worse than the loosening it prevents. What was held is **named in the success dialog** (`settings_eim_import_held`), because a silent policy is indistinguishable from an import that did not work.
| 保存復元 automation contract (headless export) | The wire contract 白い熊's automation app **白い熊 自由作業盤** (`shiroikuma.jiyusagyoban`) fires at every sister app to back them all up in one run. `settings/StateExportReceiver.java` (manifest-registered, `android:exported="true"`, **no `android:permission`** — the caller cannot hold one, the token is the gate) answers two actions: `shiroikuma.oyokanri.action.LIST_CATEGORIES` (instant; `OK:` + one `id<TAB>label` line per category — flat here, so the optional third parent-id field is always omitted) and `.action.EXPORT_STATE` (runs `SettingsBackupManager.writeExport` headlessly into **exactly ONE** zip). Directory precedence: the `path` extra → `Prefs.Storage.getSettingsExportDirectory()` → `ERROR:no-directory`; both are plain absolute paths and the app holds `MANAGE_EXTERNAL_STORAGE`, so it writes with plain `java.io.File`. `items` = comma-separated `Category.id`s (absent/empty = everything; any unknown id → `ERROR:unknown category in items: <items>`, nothing written). Reply on success: `OK:<abs path>\|<bytes>\|<human size>\|<n> categories`. **Hard-won EMUI constraints — do not "improve" them** (verified 2026-07-23): the reply is a **fresh `sendBroadcast`** with `setPackage(reply_package)` + **`FLAG_INCLUDE_STOPPED_PACKAGES`** (without it a backgrounded caller never hears us); **never** a `ResultReceiver`/`PendingIntent`/`Messenger` (EMUI may drop a broadcast carrying a live Binder outright), and the ordered-broadcast result is set but is **never the only reply** (EMUI severs that channel between third-party apps). Exactly one terminal reply per request, guarded by an `AtomicBoolean`; the work runs on a background thread under `goAsync()`. **A reply may name WHERE the data went — `location`, optional and additive (白い熊, +046).** `AppDataContract.EXTRA_LOCATION` (`"location"`) on a terminal reply says what path the callee wrote to (import) or read from (export). **First sender: 白い熊 暗記, from `2.25.0beta2+005` (2026-09-27)**: `AppDataClient` captures it in the receiver *before* offering the terminal reply, threads it through `Result` → `AppDataTransfer.Outcome` → `RestoreOp.reportAppDataOutcome`, and the restore log prints `Written to: <path>`; absence is the ordinary case and prints nothing. It rides **beside** the reply rather than inside it because the `OK:`/`ERROR:` string is the wire format forty-odd apps write, and encoding a path into it would change what that string means for all of them. **Why the contract needs it**: the channel carries content and never location, so only the callee knows where its data actually lives — an app whose data sits outside its private dirs reads and writes whatever path its *own* preferences name at that moment, and a restore that reports success while nothing appears where 白い熊 expected it cannot be told from one that worked, because nothing in the log names a path. **It names the callee's DATA LOCATION, not a user-visible collection directory** (白い熊 via the 暗記 session, 2026-09-27): 暗記's import writes only `shared_prefs/` and `files/shiroikuma_fonts/` and its export reads only those — both inside its private data dir — so from `+005` it reports `context.dataDir` (`/data/user/0/shiroikuma.anki`) on **every** terminal reply, `OK:` and `ERROR:` alike. Naming its collection under `〇/` would have been false: an import writes nothing there. The wire is unchanged (same key, beside `result`, never inside it), so nothing here needed a change. A path here is **opaque text**: displayed, never parsed, never followed. **Two loose ends on our side**: the restore log says `Written to: <path>` unconditionally, which now also prints on a **failed** import where nothing was written; and an **export** reply's path is captured and then dropped, since `BackupOp` prints no location line at all.

**LANDMINE — the progress label travels in `text`, NOT in `result` (白い熊, +181, measured across all 57 sister repos).** `result` carries the **terminal reply** and nothing else. 自由作業盤's `StateExportReceiver.kt` — the reference implementation every sister app mirrors — defines `EXTRA_PROGRESS_TEXT = "text"`, this app's own `StateExportReceiver` sends `"text"` too (line 308) with `"result"` only on the terminal reply (line 334), and a sweep found **26 of the 31** sister apps that report progress sending `"text"` alone. `AppDataClient` nevertheless read the label from `EXTRA_RESULT` for months, so it emitted one key and read another and **silently discarded the progress label of essentially the whole family** — which is why long transfers looked mute, and why two sister chats were sent to "fix" apps that were correct. `AppDataClient#progressLabel` now reads `text` and falls back to `result` (three apps send both). Do not "tidy" this back to a single key, and do not conclude from a silent transfer that the app is sending nothing. Progress (when `progress_action` is present) is **real counts, never a percentage** — `区分 i/N — <label>` with `current`/`total` (long) + `unit` extras, throttled to one per 500 ms plus a mandatory final one. `Log.d(TAG, …)` on receive + reply is the **only** on-device trace (the reply goes to another app). Gate: `settings/AutomationAuth.java` — **v2 shape (白い熊, +151), mirroring 自由作業盤's own `AutomationAuth` so every sister app behaves the same**: `shiroikuma_automation.xml` (own prefs file) holds `automation_enabled` **default true** and `automation_require_token` **default false**, plus the 24-byte `SecureRandom` hex token (generated lazily, compared **constant-time** via `MessageDigest.isEqual`). v1 shipped every app closed and a caller had to present a secret pasted out of this app's settings — which cannot survive a wipe, and the case this family now serves is 応用管理 restoring a **clean** phone, where nothing has been pasted. So the switch ships on (it stays, as the only way to close this app off) and the token is an extra a caller may be *asked* for. **A token sent to an app that does not require one is IGNORED, never refused** — tokens outlive the setting they were pasted for, and another app in the same batch may still want one; refusing would turn one switch into half a batch failing. **The whole check is `AutomationAuth.refuse(context, token)`**, returning `null` or the exact `ERROR:` line — one place, because two checks written out per entry point is how "disabled" and "bad token" drift apart across forty-odd apps. UI order: master switch · *Use an authorization token?* · the token row, which is **GONE while the requirement is off**. The prefs file stays in `EXCLUDED_PREFS`, and with these defaults that costs nothing on a migration: a fresh install comes up answering the batch with no pairing at all.</br>Historic v1 note: `SettingsBackupManager.EXCLUDED_PREFS` keeps that file out of **both** export and import, so the token never travels in a backup nor gets planted by one. UI = two rows appended **inside the Export/Import section** of the 白い熊 応用管理 UI page (never a section of its own — every sister app looks the same): the master switch, then the token row (abbreviated `8…8`, tap copies the full value, Regenerate warns pasted copies go stale) — `FontsPreferences.buildAutomationSwitchRow`/`buildAutomationTokenRow`. |

| **応用管理 is a sister app too** (白い熊, +134) | `appdata/self/OwnDataProvider.java` at `${applicationId}.automation`, plus the three `shiroikuma.automation.*` manifest metadata (contract 2, format 1 — **integers**, see the `getInt` landmine in `AppDataContract`). It exports exactly what the 保存復元 broadcast already produces: `SettingsBackupManager.writeExport`, with the same `Category` enum as the category list. **The call returns at once and the work runs behind it** — the caller blocks on a broadcast, not the binder, and here the caller is us, so a provider doing the export inside `call()` would deadlock itself; the fd is `dup()`ed before returning. **Who may come through is `appdata/self/AutomationCallers.java`** (白い熊, +153): our own uid by fast path (same uid is the same app), plus an **allowlist of exact package names** — `shiroikuma.oyokanri` and `shiroikuma.jiyusagyoban` — each cross-checked against the uid the kernel reports (`getPackagesForUid`, because packages sharing a uid are not told apart by name) **and** a pinned signing-certificate SHA-256 via `hasSigningCertificate(..., CERT_INPUT_SHA256)`. The pin matters most on the case this whole contract exists for — a clean phone, where an allowlisted package may not be installed yet and its name is a name anyone can take. **Derive a pin with `apksigner verify --print-certs` against the installed APK, never from a hash pasted into a message**; ours is `9c585f4d…c6cc`, 自由作業盤's `efd0d352…c602`. Order in `call()` is **identity → gate → dispatch**, so an unknown caller gets the same refusal for a bogus method as for a real one; another app's call also passes `AutomationAuth.refuse` (our own does not — backing ourselves up is not automation by anybody else), because "turn the switch off to close this app off entirely" has to mean the door too. Until +153 it was self-only, which meant 自由作業盤 could not back 応用管理 up through the door at all. The provider stays *exported* either way, so a stranger gets `ERROR:<reason>` rather than a `SecurityException`, which the client would report as "frozen, or no door". `AppDataTransfer` answers its own category listing directly through `StateExportReceiver.listCategories` rather than broadcasting past its own token gate, and skips preflight/restore for itself — `restore()` would otherwise be entitled to freeze this app when its backup finished. **Importing our own state is STAGED, not applied** (`PendingStateImport`): `importFrom` replaces `shared_prefs/*.xml` while this process holds them cached, and the batch runs *in this process* so it cannot hard-kill the way the Export/Import panel does. Applying it at `Application.attachBaseContext` looks safe and is not — `SecurityPrefGuard` reads current values through `AppPref` to decide what an archive may not weaken, and that read creates the cached instance the plan was avoiding. So it is offered on the next visit to the main list: Restart now / Later / Discard. |
| **The migration kit — a clean phone becomes this phone** (白い熊, +154) | `appdata/self/MigrationKit.java`. **The problem is circular**: restoring 応用管理's own state through the app backup needs Shizuku or ADB first; those need 白い熊 雫; finding 雫 needs the app configured; configuring it needs the restore. So the bootstrap rides on the **settings export**, which needs no privileges either to write or to read back, and on two plain APKs a file manager can install. Written to the backup root — `shiroikuma-oyokanri_<version>_arm64-v8a.apk`, `shiroikuma-shizuku_<version>_arm64-v8a.apk` (雫's `sourceDir` is world-readable, so its copy costs no privileges), `shiroikuma-oyokanri_state.zip` (every category, **never encrypted** — a fresh install has no key) and `shiroikuma-oyokanri_migration.json`, the only file the scan identifies a kit by (a kit written by +154 used `oyokanri-migration.json`; that name is still recognised when finding one and is removed on the next write). Refreshed from `BatchOpsService.sendResults` after **every** backup run, not only when 応用管理 backs itself up: a kit older than the archives beside it restores the wrong phone. **Pruning is 白い熊's explicit decision (2026-09-06)**, against the standing never-delete-a-build rule, and happens only after the new copy's length is verified against the source, so a failed copy can never leave neither. **LANDMINE — it must NOT depend on the previous marker's record (+156).** It did, and the marker rename in +155 promptly took that record away: `readMarker` looked only for the new name, found nothing, pruned nothing, and then deleted the legacy marker that held the answer — leaving `+154` orphaned beside `+155`. It now sweeps for **this kit's own deposit shape** for the package being deposited (the package slug, anything, then the ABI suffix), which self-heals whatever the marker says and can match neither the state archive nor the marker; the recorded name is still honoured as a second pass. **Discovery**: the configured backup directory first, then the external-storage root and **two levels** under it (the real one is two deep, `〇/979`) plus every `/storage/*` volume, skipping `Android/`; it needs all-files access to see anything, so it runs after that is granted. **The offer is gated on `looksUnconfigured()`** — no profiles, no notes, no snooping decisions — rather than on "first run", so a phone that has been used never sees it whatever is lying on its storage; the one-shot flag lives in `shiroikuma_migration`, which is in `EXCLUDED_PREFS`. **Restore** imports through `SettingsBackupManager.importFrom` and the caller hard-kills, the same rule as the Export/Import panel and `PendingStateImport`. **LANDMINE — the report cannot be built from `SharedPreferences`**: this process still holds the pre-import maps, so it counts by reading the written files (profiles directory, `shiroikuma_notes.xml`, `shiroikuma_snooping.xml`, `am_backup_directory.xml`) — the same regex-on-the-XML technique `SecurityPrefGuard` uses — writes them to `files/migration_report.txt`, and `MainActivity` renders that on the next start, including how many snooping decisions name apps that are **not installed yet** (the proof the waiting settings are really there) and whether the restored backup directory exists on this phone. The phases, written into the marker: **0.** install 雫 and make it Device Owner **before adding any account** — the one step no backup can do — **1.** install us, **2.** open and accept the restore, **3.** restore the other apps, whose snooping decisions the enforcer applies as each one installs. |
